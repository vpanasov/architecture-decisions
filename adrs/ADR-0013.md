# Decision

**В контексте** единого входа (аутентификации) сотрудников, мерчантов и внешних разработчиков в продукты greenfield-платформы Global Platform — первый этап реализуется в Backoffice Portal, далее подключаются платформенные продукты и внешние сценарии; существующий MENA-инстанс Keycloak при этом не изменяется,

**сталкиваясь с** фрагментированной аутентификацией (каждый продукт держит свой логин-стек, единого входа нет): инвертированной федерацией MENA (Keycloak брокерит на `onboarding-api` как на внешний IdP — второй эмитент с собственным ключом подписи, ROPC в цепочке, зависимость доступности логина от `onboarding-api` и Redis), отсутствием config-as-code (ручной `realm-export.json` ~3180 строк, дрейф, ревью невозможно), смешением IdP с продуктовой логикой (magic-link, рендер писем внутри Keycloak) и отсутствием единого стандарта сессий, MFA и подключения продуктов — при регуляторных требованиях сертификации платёжного контура (PCI DSS, NESA, РФ): централизованный доступ, нативный отзыв сессий ≤ 15 минут, отказ от ROPC и от второго эмитента, изоляция персональных данных по регионам и отщепляемость РФ,

**мы решили** развернуть новый чистый инстанс Keycloak **26.6.3** как чистый IdP на каждый регион (MENA, РФ, Мексика); realm по типам субъектов (`employees`, `merchants`, `internal`, `api-keys`, `partners`, тип виден в `iss`); OAuth 2.1 + OIDC с обязательным PKCE S256, hosted login, Authorization Code + PKCE для web, Device Authorization Grant (RFC 8628) без webview для мобильных, `X-Api-Key` → JWT для Public API, ROPC выключен; сквозную двойную токенизацию — внешний токен (`aud=platform-api`, TTL 15 мин) валидируется на API Gateway и обменивается по Token Exchange (RFC 8693) на внутренний токен с `aud` конкретного сервиса (кэш обмена ~60 с), внешний токен внутрь периметра не форвардится, сервис повторно валидирует внутренний токен (zero-trust); config-as-code (репозитории `platform-keycloak-image` и `platform-keycloak-config`, `keycloak-config-cli`, секреты в Vault, изменение конфигурации без рестарта); подключение продукта = два коротких MR (OIDC-клиент + роут на API Gateway) без ручного доступа к Admin Console; LoginAs как делегирование через `act`-claim (не impersonation); кастомизацию — только через штатные точки расширения (Authenticator SPI, темы), с запретом продукт-специфичных SPI и `User Storage SPI`,

**и отказались от** realm на существующем MENA-инстансе с миграцией пользователей (связанность с чужим prod, риск для работающих продуктов); развития самописной аутентификации (`onboarding-api` как OIDC-провайдер — двойной IdP, ROPC, второй эмитент, Python в сертифицируемом контуре); SaaS IdP (Auth0 / AWS Cognito / Okta — персданные у внешнего провайдера, блокер для РФ, стоимость на MAU, vendor lock-in); варианта «ничего не делать» (N собственных логин-стеков, провал сертификации, нет SSO),

**чтобы достичь** 100% входов в продукты Global Platform через единый IdP; распространения отзыва сессии ≤ 15 минут; изоляции персональных данных по регионам и отщепляемости РФ; подключения нового продукта одним MR без изменения кода платформы; воспроизводимости контура аутентификации из git без ручных шагов; сертифицируемости платёжного контура (отказ от ROPC и второго эмитента, MFA, аудит),

**принимая** ограничение кастомизации точками расширения Keycloak (свобода auth-flow обменяна на сертифицируемость и один IdP); необходимость рестарта при изменении SPI/UI (риск принудительного логаута мобильных митигируется offline-токенами, persistent user sessions и rolling/blue-green деплоем); отсутствие LTS у Keycloak OSS (политика обновлений: минор — 4 недели, патч безопасности — 2 недели); узкое место PostgreSQL под сессии (обязательны PgBouncer и отдельный инстанс БД, нагрузочное тестирование до prod); технический долг PoC-шорткатов (password grant, секреты в YAML, `start-dev`), устраняемый при переводе в целевые репозитории; а также ряд открытых вопросов, вынесенных в дочерние RFC/ADR и на согласование с ИБ и платёжной платформой (граница PCI-scope и точки интеграции, вариант A/B auth-слоя `onboarding-api`, механизм MFA/OTP, TTL offline-токенов, IP-binding сессий Shell, поток мобильного приложения, гранулярность auth-аудита, перечень критичных операций с introspection).

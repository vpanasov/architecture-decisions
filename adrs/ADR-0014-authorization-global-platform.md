# Decision

**В контексте** единого доступа (авторизации) к данным и действиям в мультитенантной мультирегиональной greenfield-платформе Global Platform (RF / MENA / LATAM) под сертификациями PCI DSS / ISO 27001 / SOC 2 — enforcement всегда «у данных», на актуальном состоянии; первым носителем полного паттерна становится shell BFF бэкофиса, далее продуктовые сервисы подключаются аддитивно через platform SDK; аутентификация (Keycloak/STS, realms, MFA, token-exchange) и m2m-взаимодействие вынесены в смежные RFC,

**сталкиваясь с** фрагментацией authn/authz по продуктам (MENA на Keycloak, РФ — собственная реализация, платежи — отдельная схема, единого способа доступа нет), точечными интеграциями с обращением сервисов в чужие БД (копии данных расходятся, изоляции тенантов нет), собственной ролевой моделью у каждого сервиса и плоской доверенной east-west сетью без сегментации — при требованиях Separation of Duties и least privilege, изоляции данных на двух уровнях (tenant — партнёр не видит чужой портфель; company — юрлицо клиента не видит данные другого) и двух фундаментальных ограничениях enforcement: проверка прав удалённым вызовом на каждом шаге цепочки дорога, а складывание всех прав в токен раздувает его и ломает мгновенный отзыв (токен действует до `exp`),

**мы решили** ввести **трёхслойную модель**: authN «кто ты» (Keycloak) → **API Gateway** валидирует токен (подпись/`aud`/срок по JWKS realm из белого списка) + token-exchange (RFC 8693) под аудиторию сервиса + маршрутизация, **роли и права не проверяет** (доменно-нейтрален) → **тонкая авторизация у данных** в co-located sidecar-**PDP** (localhost, без сетевого хопа) решает «можно ли это действие над этим ресурсом»; движок — **Cerbos** (гибрид RBAC + ABAC, политики YAML + CEL, self-hosted, structured audit из коробки, нативный .NET gRPC SDK), контракт стандартизуем по AuthZEN, но на старте работаем нативным SDK; единый декларативный `catalog.yaml` (ресурс × действие × право + governance-флаги + ABAC-атрибуты) как источник правды, из которого CI-codegen порождает политики и пик-лист, с CI-гейтом «политики ⊆ каталог»; **кастомные роли как данные** (`policy ≠ data`, композиция атомарных прав, без наследования ролей) поверх предопределённого набора (`global_admin`/`global_auditor` — сотрудники, `company_admin`/`company_auditor` — внешние); **изоляцию по двум ортогональным осям-атрибутам** `tenant_id` и `company_id` во всех fine-правилах; slim internal token под невзаимозаменяемую аудиторию сервиса; **fail-closed** (secure-by-default) с co-located sidecar и кэшем principal-context из roles-store (TTL); superuser (`global_admin`) — enforce через PDP правилом allow-all (авто-аудит в decision logs), а не bypass; доставку политик GitOps-циклом (MR → CI-гейт → controlled rollout, без egress из подов и без Cerbos Hub); асинхронный аудит решений в Kafka (топик `authz.decisions`) со сшивкой трёх потоков (Keycloak / API Gateway / PDP) единым correlationId и доставкой в SIEM; при этом MVP аддитивен — API Gateway только валидирует токен и маршрутизирует, fine-слой добавляется по-сервисно, Keycloak Authorization Services не используем,

**и отказались от** размещения всей authz (включая fine) на API Gateway (god-object, бутылочное горло, vendor lock, не масштабируется); складывания прав в токен / тонких прав в Keycloak-ролях (раздувает токены, ломает мгновенный отзыв, против рекомендаций Keycloak); чистого RBAC или чистого ABAC как единственной оси (RBAC не выражает контекст, ABAC в одиночку медленный и сложный — нужен гибрид); варианта «только библиотека в каждом сервисе без sidecar» (рассинхрон правил, нет общего журнала, обновление = передеплой); варианта «ничего не делать» (продолжение фрагментации, N ролевых моделей, невозможность PCI-сертификации единой платформы); по движку — OPA (нет first-party .NET SDK, governance-риск Styra→Apple), Cedar / AWS AVP (привязка к AWS при стеке Yandex + AWS), облачных Oso / Permit / Cerbos Hub (egress из подов, vendor-lock) и чистого графового ReBAC-движка (слабее по ABAC-полноте; ReBAC вне scope — требований на графовые связи нет),

**чтобы достичь** единого каталога прав + общего движка принятия решений + предсказуемого паттерна интеграции сервисов; изоляции tenant + company по умолчанию во всех решениях; развязки слоёв с единственным источником authz-решений (без рассинхрона Keycloak ↔ политики); онбординга нового сервиса **данными, а не кодом**; сертифицируемости платёжного контура (SoD, least privilege, fail-closed, единый аудит, исключающий недоказуемость решений); и проверяемых критериев готовности — сквозной permit + список, не менее двух deny (cross-tenant ABAC и no-permission RBAC), hot-reload политики без рестарта PDP, `catalog.yaml` → codegen → CI-валидация, корректный token-exchange, при порогах audit retention ≥ 12 мес и access-token TTL 15 мин,

**принимая** MVP-упрощение (сервис на старте доверяет API Gateway и ещё не является enforcement-границей — закрывается добавлением fine-слоя, важно не подать MVP как целевую security-модель); staleness грубой роли до `exp` токена (~15 мин), тогда как fine-права отзываются со скоростью TTL/инвалидации кэша principal-context; «без хопа» = loopback gRPC с сериализацией, а не in-process (буквальный zero-hop дал бы только embedded-движок, доступный лишь на Go — осознанно выбран единый для всех языков паттерн sidecar); повтор allow-all правила superuser в каждой resource-политике (генерится `gen.py`, не руками — у Cerbos нет глобального wildcard); технический долг (привязка к нативному Cerbos SDK вместо AuthZEN-wire; изоляция на осях-атрибутах при ещё не решённой доменной модели; MVP-доверие к API Gateway) — оформлен отдельными задачами в трекере; сознательно неприоритизированную сетевую сегментацию (NetworkPolicy инфрой пока не поддерживается — принцип «единственный путь к данным» держится на контракте и криптографии, не на сети); отложенный до продовой раскатки нагрузочный спайк и числовые SLO; а также ряд открытых вопросов и условий архкома — доменная модель иерархии tenant/инстансы; entitlement-гейт; поведение roles-store при промахе кэша (fail-closed vs grace); операционные параметры fail-closed; финальный каталог прав и ABAC-атрибуты; правила валидации кастомных ролей; формат/WORM/retention аудита и перечень событий для SIEM (сессия с ИБ); LoginAs — отдельным RFC; TMS с собственной authz-facade (mTLS + JWT) — миграция на платформенный PDP либо явный risk sign-off ИБ; согласование PCI-изменений отдельным флоу с ИБ помимо MR и CI-гейта.

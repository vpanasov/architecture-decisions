**Дата внедрения**:

# Decision

**В контексте** межсервисного (machine-to-machine) взаимодействия в мультитенантной мультирегиональной greenfield-платформе Global Platform (RF / MENA / LATAM) под сертификацией платёжного контура (PCI DSS), где пользовательский запрос сегодня аутентифицирован только до первого сервиса — публичный API Gateway обменивает внешний токен на внутренний, адресованный сервису роута ([RFC-0020](https://bz.incdb.team/pages/viewpage.action?pageId=3445883026)), — а дальше по цепочке стандарта нет ни для sync-вызовов в контексте пользователя, ни для вызовов без пользователя (cron, фоновые задачи, консьюмеры), ни для асинхронных цепочек Kafka; платформа polyglot (.NET, Python, Node.js), ожидаемое число сервисов — десятки, контур строится с нуля (миграции нет); при этом атрибуция и делегирование (клейм `act`, LoginAs) вынесены в смежный [RFC-0023](https://bz.incdb.team/pages/viewpage.action?pageId=3453550785), а тонкая авторизация — в будущий RFC (здесь только право вызова caller→target),

**сталкиваясь с** тем, что полученный сервисом токен просто переслать дальше нельзя — он адресован (`aud`) другому сервису, и принимающая сторона его отобьёт, — а без платформенного механизма каждая команда закрывает m2m по-своему (статические ключи в конфигах, самодельные подписи, форвард чужих токенов), что даёт N несовместимых схем с ручной раздачей секретов, поверх которых невозможно построить доказуемый аудит и сертифицировать платёжный контур; при двух фундаментальных ограничениях — простой форвард адресного токена ломает zero-trust, а класс атак confused deputy (посредника с широкими правами обманом заставляют применить их не по адресу) становится центральной угрозой контура,

**мы решили** ввести **модель двух потоков по типу вызова**: вызов в контексте пользователя получает целевой токен через **Token Exchange** ([RFC 8693](https://datatracker.ietf.org/doc/html/rfc8693)) — целевой сервис видит, от чьего имени действие; вызов без пользователя идёт по сервисному токену (`client_credentials`); exchange-логику команды **не пишут** — её несёт платформенный **sidecar-агент (token agent)** в поде каждого сервиса, один образ для всех стеков, сервису остаются два стандартных OAuth-действия; **правило A1** «вызывающий сервис равен адресату (`aud`) предъявленного к обмену токена» проверяет **сам Keycloak** (enforcement у IDP, не в коде); право вызова caller→target декларируется **каталогом аудиторий** в config-as-code (ревью как код, секреты в Vault); схема обмена — **`caller-owned` + `no-proxy` (sidecar)**: обмен выполняет идентичность самого вызывающего, без отдельного сетевого хопа; **митигация M2** (realm-настройка, запрещающая выданной роли молча расширить список адресатов токена) — **жёсткое предусловие MVP**; для асинхронных цепочек контекст едет **envelope** (идентификаторы `sub`/`tenant_id`/`company_id` рядом с полезной нагрузкой), а не токеном в сообщении, транспорт защищён Kafka ACL; отзыв доступа ≤ 5 минут; TLS на всех каналах с токенами/envelope — требование MVP,

**и отказались от** внутреннего API Gateway с обменом в центральной точке (`in-path`) — лишний хоп и новый Mission Critical компонент, главный аргумент «центральная точка политики» выпал на обсуждении 2026-08-10, **но вариант сохранён как путь возврата** при требовании ИБ; единого обменивающего клиента на realm (`shared`) — пропускает кейс «ошибка реализации», отклонён по итогам PoC; единого realm + межrealm-мост — требует experimental-фичи, обязательной анти-эскалационной политики и отдельного SPI; прямых вызовов + платформенный SDK без агента — polyglot превращает это в 3 SDK с exchange-логикой (ровно то, что RFC обязан исключить); только `client_credentials` везде (контекст пользователя не доезжает в подписанном виде, ломает zero-trust); только Token Exchange везде (вызовам без пользователя нечего обменивать); токена в сообщении Kafka (TTL истекает до обработки, replay, токены в брокере и DLQ); mTLS / SPIFFE вместо OAuth (второй контур доверия, не закрывает confused deputy — не замена, а фаза 2); legacy-разрешений обмена v1 (не различают вызывающих, теряют проверку адресата — проверено и отклонено на PoC); статических API-ключей (N×N секретов, нет ротации/отзыва/аудита, несертифицируемо) и варианта «ничего не делать» (стоимость бездействия растёт с каждым сервисом),

**чтобы достичь** 100% межсервисных вызовов, аутентифицированных единым платформенным механизмом; доставки контекста пользователя до каждого сервиса цепочки в подписанном токене, адресованном именно ему; независимости стоимости подключения от языка сервиса (подключение — два коротких MR, ноль auth-кода командой); декларативного контроля «кто кого вызывает» в одной точке конфигурации с ревью; отзыва доступа ≤ 5 минут; вызывающего, названного в самом токене (`azp`) как фундамента атрибуции по RFC-0023; сертифицируемости платёжного контура (каждый вызов аутентифицирован и журналируем, `auth_correlation_id` сшивает цепочку, включая асинхронные ветки); обратимости — контракт токенов не зависит от схемы обмена, возврат к центральной точке не затрагивает принимающие сервисы; при целевых порогах: вклад auth-слоя в p99 вызова ≤ 10 мс на прогретом кэше, p99 обмена ≤ 50 мс, TTL m2m-токена 5 мин, 100% подов на поддерживаемых версиях агента,

**принимая** парк агентов вместо одного деплоя (баг exchange-логики чинится раскаткой парка — митигация: один образ, версия в метриках, авто-раскатка); per-pod кэш обмена с ещё **неизмеренным hit rate** — промах даёт хвост Keycloak (~50 мс), это главная цифра этапа 1b, красные цифры = пересмотр схемы до MVP; включённый обмен у всех клиентов контура (поверхность эскалации шире, чем при обмене только у шлюза — потому M2 и становится жёстким предусловием); отсутствие per-hop журнала одной точки (аудит собирается из событий Keycloak и журналов агентов); распределённые по подам секреты обмена (радиус компрометации пода — каталог аудиторий одного сервиса); два потока вместо одного и контекст в асинхронке данными, а не криптографией (envelope подделываем инсайдером с write-доступом к топику — митигация Kafka ACL); Keycloak как критический путь по латентности (его деградация деградирует весь межсервисный трафик, HA — предусловие); зависимость от собственного плагина Keycloak (SPI), а с RFC-0023 их будет два — расход зафиксирован отдельными ADR; технический долг — критичный (процедура внеплановой ротации секретов до пилота — [Kaiten 68647924](https://life-pay.kaiten.ru/space/803288/card/68647924); внесение M2 в продуктовую конфигурацию до MVP — [Kaiten 68647929](https://life-pay.kaiten.ru/space/803288/card/68647929)) и управляемый/допустимый (эволюция к `private_key_jwt` для PCI-критичных клиентов — [Kaiten 68647966](https://life-pay.kaiten.ru/space/803288/card/68647966); envelope-стандарт Kafka — [Kaiten 68647956](https://life-pay.kaiten.ru/space/803288/card/68647956); рост каталога аудиторий как «сервисы × realm'ы» — [Kaiten 68647976](https://life-pay.kaiten.ru/space/803288/card/68647976); вложенная `act`-атрибуция до RFC-0023); увеличение числа мест внутри платформы, где обрабатывается связка псевдонимизированных ПД (`sub`/`tenant_id`/`company_id`, ст. 3 152-ФЗ, PDPL ОАЭ, LFPDPPP Мексика) — состав данных о человеке наружу не меняется, но это явное последствие решения; а также открытые вопросы и условия архкома — deny-кейс «дыры цепочки» (блокирует этап 2); вердикт предревью ИБ по центральной точке политик (положительный = возврат in-path); правовое основание обработки связки идентификаторов по всем трём рынкам до архкома; сроки хранения носителей связки и право субъекта на удаление до пилота; маппинг на требования регуляторов (ЦБ РФ, CBUAE, CNBV) до prod в платёжных сценариях; процесс ревью каталога аудиторий; условия обязательности `private_key_jwt` и подтверждение TTL 5 мин; кросс-контурные PCI-вызовы (чей IdP, точки касания).

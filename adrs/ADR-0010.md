# Decision

**В контексте** запуска карточного эквайринга на собственных терминалах PAX A950 через процессингового партнёра VaultsPay в регионе MENA,

**сталкиваясь с** регуляторными требованиями ЦБ ОАЭ (RPSCS Regulation), запрещающими Host-to-Host схему интеграции для нелицензированного PSP — Fortis не имеет лицензии Payment Service Provider в ОАЭ и не может выступать промежуточным звеном маршрутизации карточных транзакций,

**мы решили** реализовать Device-to-Host (D2H) интеграцию с VaultsPay в SDK на Android-устройстве, при которой транзакция идёт напрямую с терминала в VaultsPay, минуя Fortis PSP; SDK самостоятельно выполняет обмен RSA-ключами, аутентификацию, получение DUKPT-ключей, формирование зашифрованных транзакционных запросов, обработку ответов и Reversal; управление парком терминалов и TMS остаётся под контролем Fortis,

**и отказались от** Host-to-Host интеграции через Fortis PSP (полный контроль над маршрутизацией, централизованный мониторинг, разработка почти завершена) — заблокировано регуляторными требованиями ЦБ ОАЭ,

**чтобы достичь** запуска пилота карточного эквайринга в MENA в рамках регуляторных требований; первой живой транзакции — успешной авторизации карточного платежа с фактическим списанием средств и зачислением на счёт мерчанта; покрытия сценариев Sale/Refund/Void/Reversal/401 re-login,

**принимая** снижение стратегической гибкости — зависимость от VaultsPay как единственного транзакционного хоста (смена процессора потребует изменений в SDK, а не только на стороне хоста); необходимость новой разработки VaultsPay Connector, DUKPT Engine и RSA+AES Crypto Layer с нуля при почти завершённой H2H-реализации; необратимость RSA Key Exchange (утеря приватного ключа = ручной сброс через поддержку VaultsPay); отсутствие стандартного TTL у JWT-токена VaultsPay (повторная аутентификация только после HTTP 401); незавершённость L3 EMV-сертификации (стоимость и сроки не финализированы).

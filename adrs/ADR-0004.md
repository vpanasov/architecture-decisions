# ADR-0004: Global Merchant Portal — объединение Fortis и LP на базе единой модульной архитектуры

> Сгенерирован: AI-агент (adr-governor)
>
> **Источник:** [Confluence](https://bz.incdb.team/pages/viewpage.action?pageId=3413606406)

**Дата принятия**: 2026-04-01

**Дата внедрения**: Не внедрена

**Статус:** Accepted

# Decision

**В контексте** эксплуатации двух мерчант-порталов (Fortis для MENA и LP для РФ) с непересекающимися кодовыми базами и 206 FTE,

**сталкиваясь с** нулевым переиспользованием кода между порталами (Reuse Rate 0%), двойными затратами на разработку и исправление багов, невозможностью масштабирования на новые рынки (оба продукта захардкожены под один регион) и блокировкой инициатив по единой AI/Data платформе и Public API,

**мы решили** расширить Fortis до единой модульной платформы Global Merchant Portal с трёхслойной архитектурой: Core (единый для всех рынков, reuse ≥ 75%), Market (локальные адаптеры через provider pattern) и Store (VAS через Open API) — с принципом «Modules, not Regions», shell-приложением на Angular 20, 4 параллельными stream-aligned командами и Keycloak как единым IdP,

**и отказались от** greenfield-разработки нового продукта с нуля (18+ мес, тройное дублирование на переходный период, несовместимо с бюджетом), форка LP как основы (Custom JWT не масштабируется, page-based pagination, значительный tech debt — ~12 мес), и adapter-паттерна с фасадом поверх двух бэкендов (не устраняет корневую проблему дублирования, два бэкенда остаются навсегда),

**чтобы достичь** единой кодовой базы с двумя региональными деплойментами (MENA + RU), TTM ~12 недель на новый рынок (market preset + compliance-адаптеры, 0 правок Core), экономии ~6 месяцев по сравнению с greenfield и возможности консолидации R&D, выхода на новые рынки (KZ, UZ) и построения единой AI/Data платформы,

**принимая** параллельную эксплуатацию LP в режиме feature freeze до миграции существующих мерчантов (отдельный проект), выпуск Core GA без фискализации и маркировки (compliance выносится в Market-проекты ≤ 3 мес), overhead координации 4 стримов в shell-архитектуре, необходимость cross-training LP-команды на Keycloak/BFF/новые API-конвенции, невалидированные NFR (нагрузки и инфра-стоимость определяются на Discovery) и неопределённость DWH-архитектуры для РФ-отчётов.

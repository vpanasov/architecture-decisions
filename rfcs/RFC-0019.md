## Проблема и контекст

### Проблема

* Фрагментация authn/authz по продуктам: MENA на Keycloak, РФ — собственная реализация, платежи — отдельная схема; единого способа доступа нет.
* Сервисы ходят друг к другу точечными интеграциями и обращаются в чужие БД (либо через CRM как промежуточный склад) — копии данных расходятся, изоляции тенантов нет.
* Каждый сервис решает доступ по своей ролевой модели.
* Межсервисный трафик (east-west) идёт по плоской доверенной сети без сегментации; PCI DSS требует сегментации.

### Бизнес-обоснование

* Платформа мультитенантная и мультирегиональная (RF / MENA / LATAM) под сертификациями PCI DSS / ISO 27001 / SOC 2; ключевые принципы — Separation of Duties (SoD) и least privilege.
* Требуется изоляция данных на двух уровнях: **tenant** (партнёр не видит чужой портфель) и **company** (юрлицо клиента не видит данные другого).
* Без единого фундамента доступа продуктовые команды не могут строить сервисы на платформе.

### Контекст

Форму решения задают два фундаментальных ограничения enforcement: **(а)** проверка прав удалённым вызовом на каждом шаге цепочки — дорого; **(б)** класть все права в токен — раздувает токен и ломает мгновенный отзыв (токен самодостаточен и действует до `exp` — стандартного клейма истечения JWT, — поэтому отозванное право продолжает работать до истечения срока). Отсюда — slim internal token и решение прав всегда «у данных», на актуальном состоянии.

Сквозной принцип — **единый контракт (API) как единственный путь к данным** (no backdoor: сервис не обращается в чужую БД). UI и shell лишь потребляют контракт, а не решают доступ: скрытая во фронте кнопка это UX, а не защита — реальная проверка права всегда на backend, а прямой вызов API без права получает `deny`. Это позволяет навесить авторизацию единообразно один раз — на контракте.

Как устроено сейчас (AS IS) — разрозненная авторизация по продуктам поверх плоской сети:

> _Схема AS-IS — во вложениях исходной страницы Confluence._

### Цели / Не-цели

**Цель:** единый каталог прав + общий движок принятия решений + предсказуемый паттерн интеграции сервисов.

**Не-цели (осознанно вне этого RFC):**

* Аутентификация (login / MFA / выпуск токенов) — зона Keycloak, покрывается смежным RFC по аутентификации.
* M2M-взаимодействие (token-exchange RFC 8693, m2m trust-matrix) — отдельный заход; здесь описан только стык (см. «Границы с authn и m2m»).
* **LoginAs** (действие от имени другого пользователя) — вне MVP, отдельным заходом (стык с authn-RFC).
* **ReBAC** (авторизация по графу связей) — вне scope: требований на графовые связи нет.
* Service mesh / mTLS, полный аудит (immutable / SIEM / retention), offline-токены мобильного.
* Числовые SLO и нагрузочные замеры PDP — отдельным заходом после архкома (см. «Ресурсы и нагрузка»).

### Связь с принятыми / отклонёнными решениями

Модель проработана командой (июнь–июль 2026) и проверена работающим PoC (`poc-authz`): Keycloak realm-as-code + token-exchange, Cerbos sidecar с codegen и hot-reload, API Gateway (YARP), сквозные сценарии permit/deny. PoC — доказательство осуществимости. Смежный RFC по аутентификации покрывает эту тему.

По процессу репозитория принятый архкомом RFC порождает ADR — записи утверждённых решений появятся после архкома.

## Предлагаемое решение

Описанная ниже модель — **целевая**, не транзитная; внедрение поэтапное и аддитивное (слои не переделываются — см. «План реализации» и «Миграция / раскатка»).

### Обзор трёх слоёв

Запрос проходит три слоя: аутентификация отвечает «кто ты» (Keycloak); API Gateway валидирует токен (подпись/aud/срок) и маршрутизирует — **роли и права не проверяет**; тонкая авторизация у данных решает «можно ли это действие над этим ресурсом» (PDP: роли, права, атрибуты).

> _Схема обзора трёх слоёв — во вложениях исходной страницы Confluence._

### Модель принципалов

Кто обращается к платформе и как модель их различает — три типа принципалов:

| Принципал | Где живёт | «Роль» | Область видимости |
| --- | --- | --- | --- |
| **Сотрудник** (наш) | realm employees | внутренние роли (`global_admin` / `global_auditor`) | все tenant (`global_admin` — allow-all через PDP) |
| **Внешний-человек** (мерчант) | realm merchants | merchant-роли (`company_admin` / `company_auditor` + кастомные) | свой tenant + company |
| **Внешняя-машина** (ISV / банк, m2m) | client в realm | не «роль», а `scope` / `audience` | tenant + m2m allowlist (детали — вне scope) |

**Инвариант:** `global_admin` (superuser) — строго внутренняя роль (realm employees), внешним не выдаётся никогда. Даже MVP различает типы принципалов. Область видимости (tenant / company) ортогональна роли — применяется ко всем.

Полная топология realm, потоки логина и состав токена — в RFC по аутентификации; там же зафиксировано, что **один мерчант принадлежит ровно одной компании** (multi-company не поддерживается) — на этом строится company-изоляция.

### Границы терминов

Чтобы API Gateway не превратился в god-object, роли компонентов строго разведены:

* **API Gateway** = тонкий edge: валидация токена (подпись/aud/срок по JWKS) + token-exchange + маршрутизация + аудит. **Авторизацию (роли, права) не решает** — домена не знает.
* **Фасад** = *единственный PEP* на стороне сервиса: выставляет бизнес-метод (не сырой CRUD), вся authz-проверка через sidecar-PDP.
* **BFF** = агрегация под конкретный фронт.

`Gateway ≠ фасад ≠ BFF` — три разные роли, не один компонент.

### Границы с authn и m2m

Keycloak в роли STS (Security Token Service — выпуск и обмен токенов) — единственный issuer; он не маршрутизирует трафик и не решает fine. На входе публичный API Gateway обменивает тяжёлый внешний токен на узкий slim internal token (token-exchange, RFC 8693). **Детали m2m — вне scope этого RFC**; здесь фиксируется только стык: тонкая проверка работает с internal token одинаково, откуда бы запрос ни пришёл — снаружи (north-south) или от другого сервиса (east-west); аудитория токена (`aud`) невзаимозаменяема между сервисами.

### Проверки на API Gateway (без ролей)

API Gateway валидирует внешний токен (подпись по JWKS realm из белого списка, `aud`, срок), матчит маршрут и обменивает токен под аудиторию сервиса (token-exchange). **Роли он не проверяет** — предопределённые грубые роли едут в токене (`realm_access`, см. RFC по аутентификации), но enforcement целиком в PDP. Так нет второго источника ролевых решений (без рассинхрона Keycloak ↔ политики), а API Gateway остаётся доменно-нейтральным. Основная и единственная точка authz-решения — тонкий слой (PDP).

### Тонкая авторизация в PDP: RBAC + ABAC

Решение принимает движок-PDP рядом с сервисом (sidecar, localhost — без сетевого хопа), на актуальных данных. Модель — две оси: **RBAC** (роли = наборы атомарных прав) + **ABAC** (атрибуты: регион, среда, тип операции, тариф, а также оси изоляции tenant и company — см. «Изоляция: tenant + company»). Связи по графу (ReBAC) — вне scope: требований нет.

**Движок — Cerbos**: RBAC + ABAC, политики YAML + CEL (Common Expression Language), self-hosted, structured audit из коробки. На старте PEP обращается к нему **нативным .NET SDK (gRPC)** — оптимально и без лишних абстракций. Контракт стандартизирован AuthZEN (см. «Контракт PEP↔PDP»), что оставляет возможность сменить движок позже, но сам AuthZEN-адаптер в MVP не реализуем.

Рекомендуем Cerbos по фактуре PoC. Оговорка для честности: сравнительный спайк (Cerbos vs OPA vs OpenFGA) не проводился — PoC сразу строился на Cerbos и подтвердил пригодность. **Просим архком зафиксировать Cerbos либо назначить сравнительный спайк.** Старт без отдельного ReBAC-движка; миграция на OpenFGA/SpiceDB — по tripwires (fan-out дерева, сложность политик).

Почему Cerbos, а не другие движки (кратко): **OPA** — нет first-party .NET SDK + governance-риск (Styra→Apple, 08.2025); **Cedar / AWS AVP** — привязка к AWS (у нас Yandex + AWS); **облачные** (Oso / Permit / Cerbos Hub) — egress из подов и vendor-lock; **чистый графовый ReBAC-движок** — слабее по ABAC-полноте на старте. Контракт AuthZEN оставляет возможность сменить движок позже (маловероятно — см. «Контракт PEP↔PDP»).

### Изоляция: tenant + company

Изоляция данных — **две независимые оси-атрибута**, обе проверяются в fine-правилах:

* **tenant** — периметр партнёра (ВТБ/Альфа/Плата): пользователь не видит чужой портфель.
* **company** — юрлицо клиента (уровень над мерчантом, `company → merchant → outlet`): пользователь компании не видит данные другой компании.

В internal token кладутся `tenant_id` и `company_id`; условие в политике (generic, без конкретных id — они приходят в данных запроса):

```cel
resource.tenant_id == principal.tenant_id
&& (principal.scope == "tenant"          // сотрудник/партнёр-оператор — вся компания тенанта
    || resource.company_id == principal.company_id)
```

Роль определяет уровень видимости (см. «Роли»); superuser снимает изоляцию целиком.

> **Открыто (доменная модель):** место tenant в иерархии (узел над company или ось сбоку), single-region, и — ключевое — **единая база с иерархией vs отдельный инстанс на партнёра** (если инстансы, tenant-ось почти бесплатна). Модель изоляции построена на осях-атрибутах и корректна при любом исходе; состав scope в токене заложен расширяемым, чтобы будущий уровень не ломал контракт.

### Роли

**Предопределённый набор (нередактируемые, раздаются изначально):**

| Роль | Кто | Доступ | Как enforce |
| --- | --- | --- | --- |
| `global_admin` (superuser) | сотрудник | всё, все tenant | через PDP: allow-all правило |
| `global_auditor` | сотрудник | чтение, все tenant | через PDP |
| `company_admin` | внешний | всё в рамках своей company | через PDP (company-scope) |
| `company_auditor` | внешний | чтение в рамках своей company | через PDP |

Их не нужно прописывать в политиках вручную, и при расширении функционала им всё доступно — меньше поддержки. Поверх — **кастомные роли** (композиция атомарных прав, привязка к тенанту).

**Superuser (`global_admin`)** — самая привилегированная роль, allow-all. Enforce **через PDP**, а не в обход: `gen.py` кладёт правило `actions:["*"] roles:["global_admin"]` в каждую resource-политику (у Cerbos нет глобального wildcard `resource:"*"`, поэтому правило размножается автоматически по ресурсам каталога). Так решение остаётся в PDP — **аудит superuser-действий пишется сам** (decision logs Cerbos), без ручных аудит-костылей в SDK / API Gateway. Цена — повтор allow-all правила в политиках (генерится, не руками) и покрытие только заведённых в каталоге ресурсов. Все роли, включая `company_admin`, идут через PDP — единый источник решений и единый аудит.

### Каталог атомарных прав и кастомные роли

Единый декларативный `catalog.yaml` («ресурс × действие × право» + governance-флаги `delegatable`/`pciRestricted` + ABAC-атрибуты) — источник правды. Из него CI-codegen порождает политики движка и пик-лист в Backoffice Portal; CI-гейт проверяет «политики ⊆ каталог».

**Кастомная роль** = именованная композиция атомарных прав, привязанная к тенанту; разворачивается в эффективные права на decision-time. Ключевой принцип: `policy ≠ data` — новая роль это запись данных, политики в Git не трогаются. Модель «каталог атомарных прав + кастомные роли поверх» — референс индустрии: Stripe, Square, Shopify (гранулярные permissions + конструктор ролей в enterprise-планах).

**Наследование ролей не поддерживается** — только копирование существующей роли с последующим редактированием набора атрибутов; иерархия родитель↔потомок сознательно не вводится, чтобы не получить модель минимального доступа, в пересечениях прав которой никто не разберётся.

**PAP и roles-store** (админ-поверхность). Назначения ролей, кастомные роли и атрибуты принципала живут в **roles-store**; их редактирует **PAP** (Policy Administration Point — отдельный плагин Backoffice Portal). PDP их не даёт — эту поверхность строим отдельно (владелец — платформа). На decision-time platform SDK собирает principal-context из roles-store (с кэшем, см. «Данные и синхронизация»).

### Контракт PEP↔PDP — AuthZEN

**AuthZEN** (Authorization API 1.0, OpenID) — открытый стандарт контракта PEP↔PDP: subject/action/resource/context → permit|deny, с batch и capabilities-эндпоинтами для list/UI. Его ценность — теоретическая **сменяемость движка** без переписывания PEP.

**Что делаем на практике:** PEP работает с Cerbos через **нативный .NET gRPC SDK**, а не через AuthZEN-wire. Свой AuthZEN-клиент **не пилим** — Cerbos реализует AuthZEN для своих нужд, а писать универсальный клиент по протоколу поверх готового оптимального SDK — лишняя работа при том, что смена движка маловероятна (мы не берём ReBAC и не планируем миграцию). AuthZEN остаётся зафиксированным *как стандарт*, на который можно перейти: развязка живёт в одном месте (platform SDK), понадобится сменить движок — реализуется там.

> _Схема контракта PEP↔PDP — во вложениях исходной страницы Confluence._

### Поведение при сбое — fail-closed

Принцип — **fail-closed (secure-by-default)**: при невозможности получить решение (PDP недоступен, таймаут) доступ **запрещается**. Это продолжение deny-by-default самого движка (нет совпавшего правила → deny). Fail-open (пропускать при сбое) в authz недопустим — падение компонента не должно открывать доступ; под PCI DSS / SOC 2 это обязательный ответ на аудите. Co-located sidecar смягчает цену fail-closed: PDP в том же поде, нет удалённой зависимости — если PDP нездоров, readiness-проба выводит под из ротации, а не «мигает» отказами по сети.

Второй компонент на критическом пути fine-решения — **roles-store** (из него собирается principal-context). Прямая зависимость от него на каждый запрос снимается **кэшем с TTL**: при недоступности roles-store решения продолжают считаться на кэше до истечения TTL. Что делать при *промахе кэша + недоступности roles-store* (fail-closed vs grace на протухшем кэше — доступность ценой свежести) — операционный открытый вопрос. Параметры (таймаут PDP, circuit-breaker, TTL, поведение на промахе) — см. «Открытые вопросы».

Сводно по отказам — классического SPOF в слое нет, точка решения децентрализована per-pod:

| Компонент | Отказ | Поведение | Смягчение |
| --- | --- | --- | --- |
| PDP-sidecar | одна реплика | readiness выводит под из ротации, остальные работают | политики в памяти пода; внешних вызовов на решение нет |
| roles-store | недоступен | решения на кэше до истечения TTL; после — deny либо grace (открытый вопрос 3) | кэш с TTL; HA БД — стандарт Infra |
| Keycloak | недоступен | новые логины и token-exchange падают; уже выданные internal-токены живут до exp (~15 мин) | HA-кластер + инстанс-на-регион — смежный RFC по аутентификации |
| API Gateway | отказ реплики | stateless-реплики за LB | не SPOF при ≥2 репликах |
| Kafka (аудит) | недоступна | решения доступа не блокируются — аудит асинхронный | локальное накопление до восстановления шины (outbox) + явная фиксация потерянного интервала; поток завершается в SIEM. Открыты формат, WORM/retention и перечень типов событий (вопрос 7) |
| Git + CI | недоступен | sidecar'ы работают на текущем бандле; стоит только доставка новых политик | GitOps-откат бандла; runtime от Git не зависит |

### Данные и синхронизация

Политики (код) едут из Git через CI-бандл в каждый sidecar (controlled pull-rollout, без egress из подов, без Cerbos Hub). **Principal-context** (роли → эффективные права + атрибуты tenant/company) собирается platform SDK из **roles-store** на decision-time и передаётся в PDP в запросе — с **кэшем и коротким TTL** (назначения меняются редко, читаются часто). Живой план/фичи как ABAC-атрибуты приходят из Subscriptions (PIP). Компромисс «TTL кэша ↔ скорость доезда отзыва» и деградация roles-store — см. «Поведение при сбое» и «Ресурсы».

Для сервисов, попадающих в PCI-контур, GitOps-цикл дополняется **согласованием с ИБ**: изменения контура (добавление сервиса, пользователя, интерфейса, IP-адреса, настроек безопасности) проходят отдельный флоу согласования на стороне ИБ помимо MR и CI-гейта. Горячее обновление политик без перезапуска подов — целевое состояние; на текущем этапе новый бандл политик доезжает редеплоем, механизм pull согласуется с Infra.

## Альтернативы (рассмотренные)

Сравниваются альтернативы **архитектурной модели** доступа. Выбор конкретного движка (Cerbos vs OPA / Cedar / облачные / графовые) — не альтернатива модели, а деталь реализации; обоснование — в «Предлагаемом решении».

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
| --- | --- | --- | --- |
| ✓ Трёхслойная + RBAC/ABAC (**выбрано**) | развязывает слои, каталог как источник правды, доказано PoC | доп. слой | — |
| Вся authz на API Gateway (включая fine) | одна точка | god-object, бутылочное горло | vendor lock (Kong/Apigee), не масштабируется |
| Права в токен / тонкие права в Keycloak-ролях | нет доп. вызова | раздувает токены | ломает мгновенный отзыв, против рекомендаций Keycloak |
| Чистый RBAC / чистый ABAC (одна ось) | проще | RBAC не выражает контекст; ABAC медленный и сложный | не покрывает регион/среду/тариф либо не масштабируется — нужен гибрид |
| Только библиотека в каждом сервисе (без sidecar) | нет доп. процесса | рассинхрон правил | нет общего журнала, обновление = передеплой |
| Ничего не делать | — | продолжение фрагментации, N ролевых моделей | **невозможность PCI-сертификации** единой платформы |

## Компромиссы и технический долг

### Компромиссы

* **MVP-упрощение:** на старте сервис доверяет API Gateway и не является enforcement-границей → закрывается при добавлении fine-слоя. Важно не подать MVP как целевую security-модель.
* **Staleness грубой роли:** живёт до `exp` токена → компенсируется коротким TTL (~15 мин). Fine-права отзываются быстро (их нет в токене — решение всегда на актуальных данных), но не буквально мгновенно: скорость доезда = TTL / инвалидация кеша principal-context.
* **«Без хопа» = loopback, не in-process:** sidecar в том же поде вызывается по `localhost` (трафик не покидает под, но это всё же gRPC-вызов с сериализацией). Буквальный zero-hop дал бы только встроенный движок-библиотека, а embedded-режим Cerbos/OPA доступен лишь на Go; C# обращается к sidecar по gRPC. Компромисс осознанный: loopback работает с любым языком (единый паттерн для всех сервисов), embedded привязал бы платформу к Go, а разница латентности (микросекунды) для authz-проверки пренебрежима.
* **Superuser через PDP:** enforce правилом allow-all, а не bypass — ради единого аудита (decision logs пишутся сами). Цена — правило `actions:["*"]` повторяется в каждой resource-политике (у Cerbos нет глобального wildcard), но его генерит `gen.py`, а не руки.

### Технический долг

| Описание | Категория | План устранения |
| --- | --- | --- |
| Привязка к нативному Cerbos SDK (не AuthZEN-wire) | by design | адаптер AuthZEN — только при смене движка (маловероятно); маркер с триггером — [задача 68486521](https://life-pay.kaiten.ru/space/803288/boards/card/68486521) |
| Изоляция на осях-атрибутах при нерешённой доменной модели | управляемый | уточнить после решения по иерархии/инстансам — [задача 68486522](https://life-pay.kaiten.ru/space/803288/boards/card/68486522) |
| MVP: сервис доверяет API Gateway, ещё не enforcement-граница | staged | закрывается добавлением fine-слоя в сервис — [задача 68486523](https://life-pay.kaiten.ru/space/803288/boards/card/68486523) |

## Ресурсы и нагрузка

### Нагрузка

Топология убирает сетевой хоп: PDP по localhost внутри пода, решение локальное. Сам движок (Cerbos) считает из памяти — политики из Git, своей БД нет, чувствителен к CPU, а не к I/O. При этом данные назначений (роли → эффективные права, атрибуты) читаются из roles-store на decision-time — но это кешируемый lookup (короткий TTL, через roles-access), а не обращение к БД на каждый запрос и не внутри PDP. Настоящая per-request БД появляется только с ReBAC-движком. Кэш internal token до `exp` снижает нагрузку на token-exchange; внутренний API Gateway добавляет +1 хоп на east-west вызов (в бюджете латентности до перехода на mesh).

### Ресурсы

Числовые SLO (латентность p50/p95/p99, RPS, sizing sidecar CPU/mem) намеренно не приводятся — измеренных цифр нет. Нагрузочный спайк (синтетическое дерево 5 тенантов × 1000 мерчантов × 5 торговых точек, оценка ~1.5–2 дня) — отдельным заходом до продовой раскатки, предлагаем зафиксировать условием резолюции; целевые SLO задаём после замеров.

## Информационная безопасность

| Угроза | Мера |
| --- | --- |
| Устаревшие права после отзыва | права не в токене — решение у PDP; скорость доезда отзыва = TTL кэша principal-context (значение TTL — открытый вопрос 3); грубая роль — короткий TTL ~15 мин |
| Внешний тяжёлый токен расползается по BFF/плагинам | token-exchange только на публичный API Gateway; внутрь идёт slim internal token |
| Эскалация через кастомную роль | write-time валидация в PAP: право ∈ каталог, набор ⊆ делегируемого, ∩ тариф, ∩ PCI |
| Внешним выдали `global_admin` | `global_admin` (superuser) — строго внутренняя роль (realm employees), внешним не выдаётся никогда |
| Токен одного сервиса в другом | аудитории невзаимозаменяемы (`aud=tms` в billing → 401) |
| Кросс-тенантная / кросс-company утечка | изоляция по обеим осям (`tenant_id`, `company_id`) по умолчанию во всех fine-правилах |
| Злоупотребление привилегиями superuser | `global_admin` идёт через PDP (allow-all правило) → действия автоматически в decision logs / аудит; отдельный контроль назначения роли |
| Недоступность roles-store → отказ или протухшие права | кэш с TTL держит решения; поведение на промахе (fail-closed vs grace) — операционный вопрос |
| Непроверенное изменение правил на проде | controlled rollout: MR → CI-гейт → GitOps; не правка руками |
| Недоказуемость решений (PCI DSS / SOC 2) | structured audit-log; три потока (Keycloak / API Gateway / PDP) сшиваются единым correlation id (согласуется с `trace_id` из RFC-0001); append-only |

Полный контракт аудита — минимальный (sub/act/действие/ресурс/результат/correlationId/время); формат, WORM и retention на нашей стороне — открыто (см. «Открытые вопросы»).

**Гарантии доставки аудита.** Слой обслуживает доступ к TMS/RKL, которые относятся к Connected Tool Environment, а не к Card Data Environment (карточных данных в контуре нет), — поэтому достаточно **асинхронной публикации** в шину. Обязательные при этом требования: события **не пропадают при недоступности брокера** (локальное накопление до восстановления шины — outbox), потерянный интервал **фиксируется явно** (начало и конец периода без данных), а поток аудита завершается в **SIEM** — едином хранилище с корреляцией, в любом поддерживаемом формате (Syslog, CEF, ArcSight). Норма: на MVP допустима потеря аудита до одного дня, в целевом виде — паттерн гарантии доставки. Недоступность механизма аудита сама по себе рассматривается как инцидент с компенсирующими контролями.

**Чувствительные данные контура.** Карточные/платёжные данные слой не обрабатывает — PDP получает principal и атрибуты ресурса, необходимые правилу (id, `tenant_id`, `company_id`, тип операции), а не payload'ы; для PCI-скоупа слой авторизации — контроль доступа, не обработчик карточных данных. Политики в Git не содержат PII и секретов (`policy ≠ data`: конкретика приходит в runtime из roles-store) — компрометация репозитория политик не раскрывает чувствительного. Чувствительное в контуре: **токены** (TTL ~15 мин, slim internal token, `aud`-скоупинг), **roles-store** (запись только через PAP с write-time валидацией; TLS в транзите, шифрование at-rest — стандарт Infra) и **аудит решений** — маскирование обеспечено минимальным составом записи (payload'ы и содержимое ресурсов в аудит не попадают). Решения не покидают кластер: PDP self-hosted, без egress из подов.

**Сетевая сегментация — чего сейчас нет.** Network Policy в кластере инфраструктурой пока не поддерживается, а отдельный namespace на сервис ИБ на текущем этапе не требует (PCI DSS Guidance по контейнерной безопасности это рекомендует, и при смене аудитора возможно замечание) — внедрение сознательно не приоритизировано. Поэтому принцип «единственный путь к данным» держится не на сетевой границе, а на контракте и криптографии: сервис принимает только запросы с валидным internal-токеном под свою аудиторию, а решение о праве принимает PDP. Сетевая сегментация, когда появится, усилит эту модель, но не является её условием.

## План реализации

### Этапность

**MVP:** API Gateway валидирует токен (подпись/aud/срок) + маршрут + token-exchange — **роли не проверяет**. Предопределённые роли (`global_admin`/`global_auditor`, `company_admin`/`company_auditor`) едут в токене (`realm_access`), но enforcement — в PDP. Ролевой контроль (даже грубый) появляется с первым носителем fine-слоя (shell BFF), не использовать Keycloak Authorization Services. Кастомные роли — аддитивно позже. Шов к целевому состоянию **аддитивный**: fine-слой (SDK → Cerbos sidecar + policy-as-code + roles-store) добавляется *в сервисе* — API Gateway/Keycloak/токен не меняются.

> Это уточняет ранний внутренний план (грубая роль на API Gateway): по границе с RFC по аутентификации API Gateway роли **не** проверяет — ролевой enforcement с первого дня живёт в PDP, а не на API Gateway.

**Сервис/BFF валидирует internal token** (токен обменивается под конкретную аудиторию — zero-trust на уровне приложения: обмен на API Gateway доверия не создаёт). Базовый **шаблон BFF (dotnet template)** с преднастроенной аутентификацией и валидацией токена — общий Integration Kit (владелец — authn-контур, RFC-0001). Наш вклад — **platform SDK поверх** для fine-authz (сборка principal-context + проверка прав через sidecar-PDP); каркас SDK делаем в первую очередь, дальше расширяем.

**Первый носитель паттерна — shell BFF бэкофиса.** Живого co-located sidecar-PDP пока нет нигде (в PoC топология показана в kind как демонстрация). Первым реальным носителем полного паттерна (fine-authz через sidecar-PDP + каталог прав) становится shell BFF — на нём обкатываем модель, прежде чем тиражировать на продуктовые сервисы через platform SDK.

**PoC (Фаза 0) выполнен**: сквозной путь Keycloak → API Gateway (YARP) → сервис-фасад → Cerbos sidecar, realm-as-code + token-exchange, codegen каталога, hot-reload политик, истинный sidecar в kind (Pod 2/2). Доказательство осуществимости.

### Критерии готовности

* Сквозной запрос через API Gateway → сервис-фасад (fine-PEP) даёт permit + список.
* Не менее двух deny: чужой тенант (cross-tenant ABAC), нет права (no-permission RBAC).
* Правка политики в Git + hot-reload меняет решение без рестарта PDP.
* `catalog.yaml` → codegen → рабочие политики; CI-валидация «политики ⊆ каталог».
* token-exchange даёт internal token с нужными claims.

### Миграция / раскатка

Аддитивный шов: MVP (API Gateway только валидирует токен и маршрутизирует) не ломает существующие вызовы, fine-слой добавляется по-сервисно. Откат: fine-слой выключается на уровне сервиса (сервис возвращается к доверию API Gateway), API Gateway/Keycloak/токен при этом не затрагиваются — откат локален и не каскадный.

## Метрики успеха

База (pass/fail из критериев готовности): permit + список; ≥2 deny; hot-reload; codegen + CI-валидация; token-exchange. Смежные верифицируемые пороги: audit retention ≥ 12 мес; access-token TTL 15 мин. Числовые SLO (латентность PDP p50/p99, доступность PDP и roles-store, время доезда отзыва, % кэш-хитов principal-context) задаём после нагрузочного спайка.

Онбординг нового сервиса — **данными, а не кодом** (доказано на billing в PoC): новый Keycloak client/audience + optional scope + token-exchange + предопределённая роль + запись в карте маршрутов + ресурс в каталоге.

**Эксплуатация.** Отдельного runtime-«сервиса авторизации» нет — и это свойство решения: sidecar-PDP эксплуатирует владелец сервиса как контейнер своего пода — теми же процессами, что и сам сервис (deploy-chart поддерживает нативные sidecar'ы; платформа поставляет шаблон и метрики/алерты по умолчанию — latency решения, error-rate, всплеск deny как сигнал инцидента). Платформенные компоненты слоя — каталог, codegen, platform SDK, roles-store, PAP — эксплуатирует платформенная команда. Политики доставляются GitOps-циклом (MR → CI-гейт → controlled rollout), правок руками на проде нет.

**Наблюдаемость.** Логи решений каждый sidecar пишет нативным Kafka-бэкендом Cerbos в кластерную шину (топик `authz.decisions`); потоки Keycloak / API Gateway / PDP сшиваются единым correlationId (см. «Информационная безопасность»). Логи и ошибки контейнеров (PDP, сервис) собираются стандартным лог-пайплайном платформы; метрики PDP и SDK — латентность решения, error-rate, доля deny — отдаются в общий стек наблюдаемости, тот же, что у остальных сервисов (инструменты — зона Infra). Трассировка: authz-вызовы входят в трейсы запросов, authz-цепочки не семплируются (зафиксировано в требованиях к инфраструктуре). Дефолтные алерты поставляются вместе с sidecar-шаблоном: рост латентности решения, error-rate PDP, всплеск deny / fail-closed как сигнал инцидента. Отдельного контура наблюдаемости у слоя нет — он встраивается в платформенный.

## Открытые вопросы

1. **Доменная модель бизнес-сущностей:** место tenant в иерархии (узел над company или ось сбоку), single-region, и **единая база с иерархией vs отдельный инстанс на партнёра** — от этого зависит форма изоляции.
2. **Entitlement-гейт:** фича по тарифу — внутри PDP (как атрибут) vs отдельным шагом PDP → Entitlement в SDK. Косвенно относится к авторизации, граница с доменом биллинга.
3. **roles-store при недоступности** (промах кэша на фоне деградации store) — варианты на выбор до продовой раскатки: **(а)** строгий fail-closed: промах кэша = deny; **(б)** grace / stale-while-revalidate: обслуживание на протухшем кэше с фоновым обновлением, окно ограничено сверху. В обоих вариантах — противо-stampede меры в platform SDK: request coalescing (один промах = один запрос к store, не N), circuit breaker с backoff, джиттер TTL против синхронного истечения записей. Критерий выбора: свежесть прав (безопасность) против доступности платформы; сюда же значение TTL кэша principal-context.
4. **Fail-closed — операционные параметры:** таймаут PDP + circuit-breaker, точечные исключения (fail-open для некритичных read-only?), деградация без полного отказа.
5. Финальный каталог атомарных прав + список ABAC-атрибутов (собирается кросс-командно).
6. Правила валидации кастомной роли (каталог ∩ тариф ∩ PCI) и место enforcement.
7. Аудит: WORM / SIEM / retention / формат (факт vs diff) — отдельная сессия с ИБ. Гарантии доставки уже определены (см. «Поведение при сбое» и «Информационная безопасность»): контур обслуживает доступ к TMS/RKL — Connected Tool Environment, не Card Data Environment, — поэтому асинхронной публикации достаточно. Здесь остаются формат (факт vs diff), WORM/retention на нашей стороне и **перечень типов событий для SIEM**.
8. **LoginAs** (действие от имени другого пользователя) — вне MVP, владелец решения — отдельный RFC по login-as в контуре аутентификации. Зафиксировано: сценарий регулярный (поддержка входит от имени пользователя, чтобы воспроизвести проблему), в токене проставляется `actor` = идентификатор сотрудника, и аудит-цепочка строится по нему. Требования ИБ к тому, что сотрудник видит под чужой учётной записью (секреты и чувствительные данные не показываются), прописываются в том же RFC.
9. **TMS ведёт собственную authz-facade** (mTLS + JWT) параллельно этой модели, а не через единую точку проверки (PDP). Нужно решить: миграция TMS на платформенное SSO/PDP, либо явное исключение с отдельным risk sign-off ИБ — иначе у платформы два несинхронизированных источника authz-решений для одного потребителя.

## Критерии решения (архком)

**Просим утвердить (ядро модели):**

1. **Трёхслойная модель:** authn (Keycloak) → API Gateway (валидация токена + маршрут, без проверки ролей) → authZ в co-located sidecar-PDP.
2. **Ролевая модель:** гибрид RBAC + ABAC, каталог атомарных прав + кастомные роли; изоляция по осям tenant и company; предопределённый набор ролей.
3. **Движок — Cerbos** по фактуре PoC (либо решение назначить сравнительный спайк).
4. **Этапность MVP:** API Gateway с первого дня — только валидация токена + маршрут (без ролей); ролевой enforcement появляется с первым носителем fine-слоя (shell BFF) и добавляется в сервисы аддитивно; Keycloak Authorization Services не используем.

**Информируем (детали реализации, не требуют голосования):** контракт стандартизуем по AuthZEN, работаем нативным Cerbos SDK; `catalog.yaml` + codegen + CI-валидация; token-exchange (RFC 8693) как propagation; self-hosted дистрибуция без Cerbos Hub, sidecar per-pod; аудит — Kafka; PAP + roles-store как админ-поверхность; fail-closed; superuser с обязательным аудитом.

Модель проработана внутри команды, обкатана на PoC и рассмотрена архкомом 07.08.2026 — вердикт и условия резолюции см. в разделе «Решение архкома».

## Решение архкома

**Дата:** 2026-08-07 (заседание Architecture & Product Council).

**Вердикт:** модель принята. **Cerbos зафиксирован как единственный движок политик авторизации (PDP)** — sidecar-контейнер, RBAC/ABAC, политики как код — и внесён в техрадар; сравнительный спайк движков не назначен. Дополнительно подтверждено отсутствие ограничений по списку запрещённых технологий для регистрации ПО.

**Условия и требования, зафиксированные на заседании:**

* **Аудит:** асинхронной публикации достаточно — контур обслуживает доступ к TMS/RKL (Connected Tool Environment, не Card Data Environment). Обязательны: локальное накопление событий при недоступности брокера, явная фиксация потерянного интервала, доставка потока в SIEM. Норма: на MVP допустима потеря аудита до одного дня, в целевом виде — паттерн гарантии доставки; недоступность механизма аудита рассматривается как инцидент с компенсирующими контролями.
* **PCI-контур:** изменения (добавление сервиса, пользователя, интерфейса, IP-адреса, настроек безопасности) согласуются с ИБ отдельным флоу помимо MR и CI-гейта.
* **LoginAs:** сценарий признан регулярным; требования ИБ к тому, что сотрудник видит под чужой учётной записью, выносятся в отдельный RFC по login-as.
* **Технический долг:** оформлен отдельными задачами в трекере, ссылки — в разделе «Технический долг».

**Осталось открытым (вне этого RFC):** форма межсервисного обмена токенами — внутренний API Gateway против sidecar рядом с сервисом — вынесена на следующее заседание вместе с RFC по m2m-аутентификации; внедрение Network Policy в кластере признано неприоритетным на текущем этапе. Даты утверждения и срока действия в шапке документа заполняет координатор процесса.

## Глоссарий

Основные термины документа (для читателей из разных областей):

| Термин | Значение |
| --- | --- |
| **authN / authZ** | аутентификация («кто ты») / авторизация («что тебе можно») |
| **fine authZ** | тонкая авторизация: роли, ресурс, атрибуты — решение в PDP (API Gateway роли не проверяет) |
| **RBAC / ABAC** | доступ по ролям / по атрибутам (регион, тариф, tenant, company) |
| **PEP** | Policy Enforcement Point — точка, перехватывающая запрос и спрашивающая разрешение |
| **PDP** | Policy Decision Point — движок, принимающий решение permit/deny |
| **PAP** | Policy Administration Point — где заводят и редактируют роли и назначения (админ-поверхность) |
| **PIP** | Policy Information Point — источник атрибутов для решения (например, план/фичи из Subscriptions) |
| **roles-store** | хранилище назначений ролей и principal-context (read-сторона для решения) |
| **principal** | субъект запроса; три типа: сотрудник, внешний-человек (мерчант), внешняя-машина (m2m) |
| **AuthZEN** | открытый стандарт (OpenID) контракта между PEP и PDP; на старте не реализуем — работаем нативным SDK Cerbos |
| **Cerbos** | выбранный движок принятия решений (PDP) — политики как код, self-hosted |
| **superuser** | самая привилегированная роль (`global_admin`): allow-all, enforce правилом в PDP (см. «Роли») |
| **entitlement** | доступность фичи по тарифу (в отличие от права — permission); косвенно влияет на доступ |
| **sidecar** | вспомогательный контейнер рядом с сервисом в том же поде (вызов по localhost) |
| **STS** | Security Token Service — сервис выпуска и обмена токенов (роль Keycloak) |
| **token-exchange (RFC 8693)** | обмен одного токена на другой — под нужную аудиторию/scope |
| **JWKS** | набор публичных ключей для проверки подписи токена |
| **north-south / east-west** | трафик снаружи внутрь (клиент → платформа) / между сервисами внутри |
| **tenant / company** | периметр партнёра (ВТБ/Альфа/Плата) / юрлицо клиента — две оси изоляции |

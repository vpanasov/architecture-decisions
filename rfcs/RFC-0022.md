## Проблема и контекст

### Проблема

Пользовательские запросы аутентифицированы только до первого сервиса: публичный API Gateway обменивает внешний токен на внутренний, адресованный сервису роута ([RFC-0020](https://bz.incdb.team/pages/viewpage.action?pageId=3445883026)). Дальше стандарта нет:

* **Вызов сервисом сервиса в цепочке запроса пользователя** — чем аутентифицируется и как до следующего сервиса доезжает контекст пользователя, не определено. Просто переслать полученный токен нельзя: он адресован другому сервису, и принимающая сторона его отобьёт.
* **Вызовы без пользователя** (cron, фоновые задачи, консьюмеры событий) — механизма нет вообще.
* **Асинхронные цепочки (Kafka)** — как атрибутировать событие пользователю и чем аутентифицируется консьюмер, не определено.

Без платформенного решения каждая команда закрывает это по-своему: статические ключи в конфигах, самодельные подписи, форвард чужих токенов. Результат — N несовместимых схем, ручная раздача секретов и невозможность построить поверх этого доказуемый аудит.

### Бизнес-обоснование

* **Кто заказчик:** техническая необходимость платформы (Admin Platform) плюс требование сертификации платёжного контура.
* **Бизнес-цель:** единый механизм межсервисной аутентификации — предпосылка атрибуции действий ([RFC-0023](https://bz.incdb.team/pages/viewpage.action?pageId=3453550785)), которую требует аудит PCI DSS, и снятие с продуктовых команд проектирования межсервисного auth (платформа polyglot: .NET, Python, Node.js).
* **Стоимость бездействия:** каждая команда изобретает свою схему — N схем с ручной раздачей секретов вместо одной точки конфигурации; поверх зоопарка аудит не строится, платёжный контур несертифицируем.

### Термины

| Термин | Значение |
| --- | --- |
| Токен (JWT) | Подписанный Keycloak «пропуск». Ключевые поля: `sub` — от чьего имени действие; `aud` — какому сервису адресован; `azp` — какой клиент его получил. Содержимое не подделать. |
| Обмен токена (Token Exchange, [RFC 8693](https://datatracker.ietf.org/doc/html/rfc8693)) | Штатная операция Keycloak: клиент предъявляет токен, выписанный для одного сервиса, и получает новый — для другого. Права при обмене не расширяются. |
| Обменивающий клиент | Клиент Keycloak, от имени которого выполняется обмен. Кто им является — главный архитектурный выбор этого RFC. |
| Каталог аудиторий | Декларативный перечень адресатов, на которые обменивающему клиенту разрешено получать токены. Проходит ревью как конфигурация. |
| Правило A1 | Вызывающий сервис обязан совпадать с адресатом (`aud`) токена, который он предъявляет к обмену. В ранних редакциях — «инвариант A1». |
| Ось A / Ось B | Две развилки решения: чья идентичность выполняет обмен (`shared` / `per-caller@gw` / `caller-owned`) и где обмен относительно пути вызова (`in-path` / `no-proxy`). Вместе — схема обмена. Рекомендация: `caller-owned` + `no-proxy` (sidecar). |
| Митигация M2 | Настройка realm'а, не позволяющая выданной роли молча расширить список адресатов токена. Один декларативный блок на realm. |
| Sidecar (token agent) | Платформенный агент в поде сервиса: держит секрет клиента, кэширует и обменивает токены. Один образ для всех стеков; сервис с Token Exchange не работает вообще. |
| Confused deputy | Класс атак: посредника с широкими правами обманом заставляют применить их не по адресу. Центральная тема безопасности этого RFC. |
| Envelope (Kafka) | Служебная обёртка события: идентификаторы из клеймов токена, которые продюсер кладёт рядом с полезной нагрузкой; по ним консьюмер восстанавливает контекст. |
| ROPC | Устаревший поток OAuth с передачей пароля приложению. В межсервисном контуре отсутствует как класс. |
| SPI | Собственный плагин Keycloak. Ограниченный ресурс: каждый новый — только через ADR. |
| Zero-trust | Каждый сервис сам валидирует входящий токен и не доверяет вызывающему по факту нахождения внутри контура. |
| Greenfield | Контур строится с нуля: стандарт закладывается до первого межсервисного вызова — миграции нет. |
| Polyglot | Сервисы платформы пишутся на разных языках, платформенная логика не может жить в SDK одного стека. |
| Mission Critical | Компонент на критическом пути вызова: его отказ останавливает обслуживание, требует HA и отдельного бюджета надёжности. |
| Hit rate (кэша) | Доля обращений, обслуженных кэшем без запроса к Keycloak; от неё зависит вклад auth-слоя в латентность. |

### Контекст

Наследуемые решения [RFC-0020](https://bz.incdb.team/pages/viewpage.action?pageId=3445883026), на которые опирается этот RFC: realm `internal` для сервисных аккаунтов; Token Exchange (обкатан на публичном API Gateway); zero-trust-валидация на каждом сервисе; config-as-code (клиенты Keycloak — YAML с ревью, секреты — Vault); сквозная auth-корреляция.

Дополнительно: сервисы не только на .NET (также Python и Node.js); ожидаемое число сервисов — десятки. Контур greenfield: межсервисных вызовов ещё нет, стандарт закладывается до первого — миграция не требуется.

#### Цели / Не-цели

**Цели:** 100% межсервисных вызовов аутентифицированы платформенным механизмом; контекст пользователя доезжает до каждого сервиса цепочки в подписанном токене, адресованном именно ему; стоимость подключения не зависит от языка сервиса; подключение — два коротких MR, auth-код командой не пишется; отзыв доступа ≤ 5 минут; право «кто кого вызывает» задекларировано в конфигурации и проходит ревью.

**Не-цели:** атрибуция и делегирование (клейм `act`, LoginAs) — [RFC-0023](https://bz.incdb.team/pages/viewpage.action?pageId=3453550785); тонкая авторизация — будущий RFC (здесь только право вызова caller→target); аутентификация транспорта Kafka — зона инфраструктуры; кросс-контурные вызовы в PCI-скоуп — с платёжной платформой и ИБ; аутентификация внешних потребителей — покрыта RFC-0020.

### Связь с принятыми / отклонёнными решениями

* **Развивает [RFC-0020](https://bz.incdb.team/pages/viewpage.action?pageId=3445883026)**: заполняет отложенную там нишу m2m, не меняя его решений. Паттерн «обмен выполняет шлюз» для внутреннего трафика этой редакцией **не** переиспользуется: внутри контура обмен выполняет sidecar-агент идентичностью самого вызывающего.
* **Дополняется [RFC-0023](https://bz.incdb.team/pages/viewpage.action?pageId=3453550785)** (клейм `act`, LoginAs). Зависимость односторонняя: этот RFC самодостаточен до prod-этапа в платёжных сценариях.
* **Что пересматривается.** Ранее согласованных решений платформы RFC не отменяет. Пересмотрены три собственных вывода предыдущих редакций: (1) от единого обменивающего клиента на realm (`shared`) отказались по итогам PoC — кейс «ошибка реализации» он пропускает; (2) вывод «цепочка LoginAs покрывается вложенностью обмена» опровергнут измерением; (3) рекомендация второй редакции — внутренний API Gateway — пересмотрена по итогам обсуждения 2026-08-10: рекомендуется sidecar, без лишнего хопа и нового Mission Critical компонента; центральная точка возвращается как вариант при требовании ИБ.

## Предлагаемое решение

На утверждение выносится: модель двух потоков по типу вызова, правило A1 и схема обмена sidecar (`caller-owned` + `no-proxy`) — в связке с митигацией M2 как жёстким предусловием MVP.

Вызов в контексте пользователя получает токен через обмен: целевой сервис видит, от чьего имени действие. Вызов без пользователя идёт по сервисному токену. Exchange-логику команды не пишут — её несёт платформенный sidecar-агент в поде каждого сервиса, один артефакт для всех стеков; сервису остаются два стандартных OAuth-действия. Правило A1 «вызывающий равен адресату предъявленного токена» проверяет сам Keycloak. Право вызова caller→target декларируется каталогом аудиторий в конфигурации (ревью как код).

Внутренний API Gateway (`in-path`) не строится: лишний сетевой хоп и новый Mission Critical компонент не появляются. Он остаётся документированным вариантом возврата, если ИБ предъявит требование центральной точки политик. Модель двух потоков, правило A1 и контракт токена от схемы обмена не зависят — они не меняются, кто бы физически ни выполнял обмен.

### Схема зависимостей

**Контейнеры контура и вызовы между ними.** Пунктир «ПД» — единственная стрелка с прямым ПД (вход пользователя); остальные несут токен со связкой `sub`/`tenant_id`/`company_id` — псевдонимизированным ПД, одинаковым на всём пути (см. «Персональные данные»).

**Основной поток — вызов в контексте пользователя:** сервис A отдаёт user-токен своему агенту; агент обменивает его идентичностью svc-a, правило A1 сверяет сам Keycloak.

### Что показал PoC

Три раунда на dev-образе платформы (Keycloak 26.6.3 / 26.7.1):

* Кейс «ошибка реализации» (предъявлен токен, адресованный не вызывающему): при `caller-owned` и `per-caller@gw` его отбивает сам Keycloak (403), при `shared` — проходит. Правило A1 держит IDP, не код.
* Вся цена вызова — обмен: ~4 мс p50, до ~50 мс p99 в хвосте Keycloak; сам дополнительный хоп — десятые доли миллисекунды. Отсюда главный вопрос этапа 1b: hit rate per-pod кэша.
* Попытка получить при обмене больше прав, чем нёс исходный токен, отбивается штатным механизмом Keycloak до выпуска токена (400) — при любой схеме обмена.
* Legacy-разрешения обмена (v1) проверены и отклонены: вызывающих не различают, проверку адресата теряют.
* Межrealm-мост (раунд 3) технически подтверждён, но требует experimental-фичи, обязательной анти-эскалационной политики и отдельного SPI — не выбран в этой редакции.

### Открытые вопросы

| Вопрос | Решение за |
| --- | --- |
| Deny-кейс «дыры цепочки»: подтвердить, что цепочка переобменов ограничена каталогом каждого звена (этап 1b, блокирует этап 2) | Команда + ИБ |
| Требование ИБ к центральной точке политик/журнала — вердикт предревью до этапа 2; положительный = возврат варианта in-path | ИБ |
| Сроки хранения носителей связки идентификаторов (Kafka/DLQ, Audit Log, журналы агентов) и право субъекта на удаление — до пилота | Юрист + ИБ + Инфраструктура |
| Правовое основание обработки связки идентификаторов: 152-ФЗ + PDPL (ОАЭ) + LFPDPPP (Мексика) — до архкома | Юрист + ответственный за ПД |
| Маппинг на требования регуляторов рынков (ЦБ РФ, CBUAE, CNBV) — до prod в платёжных сценариях | Комплаенс + ИБ |
| Процесс ревью каталога аудиторий (кто апрувит новое право вызова) | Admin Platform + ИБ |
| `private_key_jwt` для PCI-критичных клиентов: когда обязателен | ИБ + команда |
| TTL m2m-токена 5 мин — подтвердить | ИБ |
| Envelope-стандарт Kafka: формат principal-блока, версионирование | Команда |
| Кросс-контурные вызовы PCI: чей IdP, точки касания | Платёжная платформа + ИБ |
| Процедура внеплановой ротации секретов при их числе «сервисы × регионы × realm'ы» | Admin Platform + ИБ |

### Критерии решения (архком)

* **Сертифицируемость**: каждый вызов аутентифицирован, декларативный контроль «кто кого вызывает» в одной точке конфигурации, отзыв ≤ 5 мин, вызывающий назван в самом токене — фундамент для атрибуции (RFC-0023).
* **Time-to-market и polyglot**: подключение сервиса — два MR, ноль auth-кода, одинаково для любого стека.
* **Стоимость владения**: один платформенный агент против центрального Mission Critical компонента, трёх SDK или N самодельных схем; цена — эксплуатация парка, верифицируется этапом 1b.
* **Полнота**: покрыты все классы вызовов — sync с пользователем, service-initiated, асинхронка, граница PCI.
* **Обратимость**: контракт токенов не зависит от схемы обмена — возврат к центральной точке не меняет принимающие сервисы. Оговорка: решение опирается на собственный плагин Keycloak (и с RFC-0023 их будет два) — расход зафиксирован отдельными ADR.

## Альтернативы

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
| --- | --- | --- | --- |
| Внутренний API Gateway (обмен в центральной точке) | Exchange-логика в одном месте; центральная точка политики и журнала | +1 хоп; новый Mission Critical компонент; мощный обменивающий клиент; миграция на sidecar «потом» — дорогая | Отклонена как MVP-дефолт по итогам обсуждения 2026-08-10: главный аргумент — центральная точка политики — выпал. **Сохранена как вариант возврата** при требовании ИБ |
| Единый realm для сервисов + межrealm-мост | Каталог не растёт как «сервисы × realm'ы»; одна точка отзыва | Experimental-фича; без обязательной политики эскалирует scope; кастомные клеймы не переживают мост — нужен отдельный SPI | Механика подтверждена PoC, но два новых предусловия не дешевле действующей схемы; кандидат отдельного трека |
| Прямые вызовы + платформенный SDK (без агента) | Нет хопа и нового компонента | Polyglot = 3 SDK с exchange-логикой; синхронные релизы N библиотек | Exchange-логика в коде каждого стека — ровно то, что RFC обязан исключить |
| Только `client_credentials` (сервисные аккаунты везде) | Простейший онбординг | Контекст пользователя не доезжает в подписанном виде; ломает zero-trust; атрибуция невозможна | Контекст нужен для авторизации и сертификации |
| Только Token Exchange (обмен везде) | Один механизм | Вызовам без пользователя нечего обменивать | Не закрывает половину сценариев |
| Токен в сообщении Kafka | Подписанный контекст в асинхронке | TTL истекает до обработки; replay; токены в брокере и DLQ | Риски перевешивают; контекст едет envelope, транспорт защищён ACL |
| mTLS / SPIFFE вместо OAuth | Транспортная идентичность без токенов | Второй контур доверия параллельно Keycloak; не закрывают confused deputy | Не конкурент и не замена: фаза 2 phased target |
| Legacy-разрешения обмена (v1) | Тонкие разрешения на стороне IDP | Вызывающих не различают; теряется проверка адресата | Проверена и отклонена на PoC: размен в минус |
| Статические API-ключи | Нет зависимости от Keycloak в runtime | N×N секретов; нет ротации, отзыва, аудита | Несертифицируемо; масштабируется квадратично |
| Ничего не делать | Нет затрат сейчас | N несовместимых схем, ручные секреты, аудит не строится | Стоимость бездействия растёт с каждым сервисом |

## Компромиссы и технический долг

### Компромиссы

Первые четыре — цена sidecar-варианта (пересматриваются вместе с решением архкома по схеме обмена), остальные — цена самой модели:

* **Парк агентов вместо одного деплоя**: баг exchange-логики чинится раскаткой парка. Митигация: один образ, версия агента в метриках, авто-раскатка.
* **Per-pod кэш обмена с неизмеренным hit rate**: промах = хвост Keycloak (~50 мс). Главная цифра этапа 1b; красные цифры — пересмотр схемы до MVP.
* **Обмен включён у всех клиентов контура**: поверхность эскалации шире, чем при обмене только у шлюза — поэтому митигация M2 становится жёстким предусловием MVP.
* **Per-hop журнала одной точки нет**: аудит собирается из событий Keycloak и журналов агентов; `auth_correlation_id` связывает цепочку, `azp` называет вызывающего — атрибуция беднее не становится.
* **Секреты обмена распределены по подам** (Vault-инъекция): радиус компрометации одного пода — каталог аудиторий одного сервиса.
* **Два потока вместо одного**: единый механизм не покрывает оба сценария; для сервиса разница — передать или не передать user-токен.
* **Контекст в асинхронке — данными, не криптографией**: envelope подделываем инсайдером с write-доступом к топику; митигация — Kafka ACL + контракт схемы.

## Ресурсы и нагрузка

### Нагрузка

* Сервисные токены — кэш агента до TTL: обновление раз в ~5 минут на сервис, нагрузка на Keycloak ~нулевая.
* Обмены — по одному на хоп цепочки, кэш per-pod (~60 с); hit rate не измерен — этап 1b.
* **Keycloak — критический путь по латентности**: вся цена вызова — обмен (~4 мс p50, до ~50 мс в хвосте). Деградация Keycloak деградирует весь межсервисный трафик; HA — предусловие, а не улучшение.
* Входные пороги этапа 1b: ожидаемый профиль — порядка сотен межсервисных запросов в секунду на регион в пике первых волн; целевой p99 обмена ≤ 50 мс; главный измеряемый параметр — hit rate per-pod кэша.

### Ресурсы

* Sidecar-агент: новый платформенный компонент — репозиторий, образ, Helm-инъекция; ресурсы в каждом поде подключённого сервиса (лимиты фиксируются на этапе 1b).
* Keycloak, Vault, config-pipeline — существующие (RFC-0020).
* Integration Kit: агент, m2m-модуль в dotnet-шаблоне, рецепты Python/Node.js.

## Информационная безопасность

* **Хранение/обработка ПД:** Да. Прямые ПД (логин — в Fortis это может быть номер телефона — и email) хранятся на стороне Keycloak. Межсервисные токены прямых ПД не переносят, но переносят псевдонимизированные — см. «Персональные данные».
* **Поток ПД (верхний уровень):** прямые ПД остаются в Keycloak и сервисах-владельцах; по контуру летят идентификаторы (`sub`, `tenant_id`, `company_id`) — стабильная связка, псевдонимизированные ПД по ст. 3 152-ФЗ. Обрабатывается везде, где проходит: агенты, сервисы цепочки, Kafka/DLQ, Audit Log, логи.
* **Публичное API:** Нет — внутренний контур; внешний трафик остаётся на публичном API Gateway (RFC-0020).
* **Основные угрозы:** confused deputy, компрометация обменивающего клиента, форвард адресного токена дальше по цепочке, подделка envelope в Kafka инсайдером.
* **Меры защиты:** правило A1, адресность токена (`aud`), запрет legacy-обмена v1, секреты в Vault с ротацией, право вызова в config-as-code с ревью, Kafka ACL, аудит каждого обмена.

### Персональные данные

Два уровня, путать нельзя. **Прямые ПД** — логин (может быть номером телефона) и email: их хранит и обрабатывает Keycloak и сервисы — владельцы данных. Решение не создаёт ни нового места хранения, ни нового обработчика прямых ПД, ни передачи за пределы платформы; в межсервисные токены логин и email не попадают.

**Псевдонимизированные ПД** — то, что действительно ходит между сервисами: идентификаторы субъекта, арендатора и компании. Связка стабильна, повторяется в каждом вызове и позволяет связать действие с конкретным человеком — подпадает под широкое определение ПД ст. 3 152-ФЗ, а также PDPL (ОАЭ) и LFPDPPP (Мексика). Правовое основание её обработки (рабочая гипотеза — законный интерес оператора / исполнение договора) подтверждает ИБ/ответственный за ПД **до архкома** — по всем трём рынкам.

Региональная граница фиксируется нормативно: токены, envelope и журналы не покидают контур своего региона; централизация аудита между регионами, если появится, оформляется отдельным решением. Сроки хранения носителей связки и позиция по праву субъекта на удаление — открытый вопрос за юристом, ИБ и Инфраструктурой, закрыть до пилота.

Что меняется по итогу: межсервисные вызовы становятся аутентифицированными и журналируемыми; состав данных о человеке, которые платформа хранит и передаёт наружу, не меняется, но число мест внутри платформы, где обрабатывается связка идентификаторов, увеличивается — это явное последствие решения.

### Детали для ИБ

* Каждый вызов аутентифицирован; целевой сервис получает подписанный контекст пользователя, адресованный именно ему. Право вызова — декларативно в config-as-code, enforcement — сам Keycloak; отзыв ≤ 5 мин.
* **Шифрование в транзите — требование MVP, не фазы 2**: все каналы с токенами или envelope (сервис↔сервис, агент↔Keycloak, агент↔Vault, продюсер/консьюмер↔Kafka) — TLS уже на MVP. Кэши агента живут только в памяти пода. Шифрование в покое для Kafka/DLQ и Audit Log — включено до пилота либо явный risk acceptance ИБ.
* **Журнал агента не содержит значений токенов**: логируются `jti`, `azp`, `aud`, `auth_correlation_id` и результат; сами токены — никогда.
* **Размещение секретов**: клиент каждого сервиса существует в realm'е `internal` и в каждом realm'е пользователей каждого региона; секреты держит агент через Vault-инъекцию. Радиус поражения одного секрета — каталог аудиторий одного сервиса в одном realm'е.
* Исходные токены внутрь целевого сервиса не форвардятся; вызов без валидного адресного токена отбивается на самом принимающем сервисе — центральной точки в пути вызова нет, обходить нечего.
* `token-exchange:v1` строго хуже v2 и запрещён (подтверждено измерением); ROPC и статические ключи отсутствуют как класс.
* Все выпуски и обмены токенов — в event log Keycloak, далее в Audit Log; `auth_correlation_id` связывает цепочку, включая асинхронные ветки.
* RFC до архкома проходит предварительное ревью ИБ.

## План реализации

Привязка к этапам RFC-0020 (realm `internal` закладывается там). Фактический следующий этап — 1b; при возврате архкома к центральной точке этап 2 заменяется на «Внутренний API Gateway MVP».

| Этап | Содержимое | Цель |
| --- | --- | --- |
| 1 — PoC (**выполнен**) | Механика обмена, латентность, TTL; три варианта схемы обмена на одном стенде; правило A1, каталог аудиторий, M2, legacy-политики | Развилки закрыты до архкома |
| 1b — Верификация sidecar-профиля | Прототип агента на стенде: hit rate per-pod кэша, p99 под fan-out, поведение при отказе Keycloak, ресурсная цена агента; deny-кейс «дыры цепочки» | Подтвердить рекомендацию цифрами до MVP; красные цифры — возврат к сравнению вариантов |
| 2 — Sidecar-агент MVP | Репозиторий, образ, Helm-инъекция, Vault-инъекция секретов; M2 в продуктовой конфигурации и зелёный deny-кейс «дыры цепочки» — блокирующие условия старта | Межсервисный вызов через агента на dev |
| 3 — Integration Kit | m2m-модуль dotnet-шаблона, рецепты Python/Node.js, тип «m2m-сервис» в скаффолдинге, envelope-стандарт Kafka | Команда подключает m2m по документации сама |
| 4 — Пилот | Первая пара продуктовых сервисов (разных стеков) на обоих потоках | Подтверждение polyglot-стоимости |
| 5 — Prod | Нагрузочный тест, канал обновления парка, runbook ротации, аудит-события | Продуктивная эксплуатация |

### Оценка трудозатрат

Не оценено (осознанный ответ автора).

### Зависимости от других команд

* **ИБ**: предварительное ревью; решения по `private_key_jwt` и TTL. Вопросы достоверности атрибуции — RFC-0023, отдельным треком.
* **Инфраструктура**: Helm-механика инъекции агента и ресурсные лимиты; TLS внутри кластера для каналов с токенами/envelope (требование MVP); шифрование в покое Kafka/DLQ и Audit Log — до пилота; Kafka ACL; ёмкость PostgreSQL под exchange-профиль.
* **Платёжная платформа**: правило касания PCI-границы.
* **Продуктовые команды**: пилот на первой паре сервисов, включая не-.NET стек.

Влияние на команды: продуктовые команды получают m2m через агента в поде (два MR + стандартная OAuth-либа стека, собственные схемы не строятся); Admin Platform владеет агентом, Integration Kit, ревью каталогов и runbook'ами; ИБ — предревью и решения по TTL/`private_key_jwt`; Инфраструктура — Helm-инъекция, ресурсы парка, Kafka ACL.

### Критерии готовности

* Пилотная пара сервисов (включая не-.NET) работает на обоих потоках.
* Подключение m2m выполнено командой по документации без участия Admin Platform.
* Нагрузочный тест межсервисного профиля пройден до prod; латентность хопа в бюджете.
* Отзыв клиента и снятие права вызова — проверены, действуют ≤ 5 мин.
* Deny-тесты правила A1 пройдены (4 кейса, включая «дыру цепочки» и запрет превышения прав субъекта); вместе с M2 в продуктовых realm'ах — блокирующие условия старта этапа 2.
* До prod в платёжных сценариях — атрибуция по RFC-0023 принята и включена; пилот возможен без неё.

### Миграция / раскатка

Greenfield: стандарт закладывается до первого межсервисного вызова — миграции нет. Откат на любом этапе безопасен: не подключённые сервисы ничего не теряют. Запасной вариант при проблемах парка агентов — центральная точка обмена (внутренний API Gateway): контракт токенов не меняется, принимающие сервисы не затрагиваются.

### Цена отката

* **Конфигурация** (клиенты, каталоги аудиторий, скоупы) — восстанавливается из git на любой хеш: цена отката равна одному MR.
* **Подключённые сервисы** — подключённая пара откатывается снятием инъекции агента; контракт токенов не меняется.
* **Митигация M2** — единственный шаг, который не откатывается конфигурацией: удаление требует Keycloak Admin API, явный пункт runbook.
* **Sidecar-агент** — потраченное на компонент не возвращается, поэтому решение по схеме обмена принимается до пилота, на цифрах этапа 1b.

## Метрики успеха

* **Бизнес-метрики:** техническое решение без прямого влияния на бизнес-метрики — эффект опосредованный: сертифицируемость платёжного контура и стоимость подключения новой команды.
* **Технические метрики:** 100% межсервисных вызовов аутентифицированы платформенным механизмом; подключение сервиса — два MR, ноль auth-кода, независимо от языка; отзыв доступа ≤ 5 минут; вклад auth-слоя в p99 вызова — в бюджете 10 мс на прогретом кэше; hit rate per-pod кэша не ниже порога этапа 1b; 100% подов на поддерживаемых версиях агента.

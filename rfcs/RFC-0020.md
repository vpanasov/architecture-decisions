## Проблема и контекст

### Проблема

Аутентификация в продуктах фрагментирована: каждый продукт держит свой логин-стек, единого входа для сотрудников и мерчантов нет. Ключевые дефекты текущей реализации:

* **Инвертированная федерация (MENA).** Keycloak брокерит на Python-сервис `onboarding-api` как на внешний OIDC IdP. Реальная цепочка (по канонной схеме self-service «Переход к странице авторизации», см. Источники): проверка пароля — обратным вызовом в Keycloak через отдельно заведённый клиент (ROPC); затем `onboarding-api` формирует промежуточный JWT, подписанный собственным ключом (RS256, exp 1 ч), который Keycloak однократно валидирует по JWKS самого сервиса. Клиент всегда получает токен Keycloak; сессия и политики отзыва — Keycloak; промежуточный JWT — одноразовый артефакт брокеринга (аналог id\_token внешнего IdP). Дефект не в том, чей токен у клиента, а в топологии: (1) внутри контура — второй эмитент с собственным ключом подписи: компрометация ключа `onboarding-api` = вход в учётки Keycloak (внешний брокеринг типа Google такого риска не несёт — сторонний IdP сам держит пароли и не проверяет их обратным вызовом); (2) ROPC в цепочке (исключён из OAuth 2.1); (3) доступность логина зависит от `onboarding-api` и Redis. Команда self-service сама квалифицирует схему «signin как внешний IdP» как архитектурно некорректную и непригодную для production. Применимость политик отзыва Keycloak к сессиям self-service — уточнить с командой self-service (дочерний ADR по auth-слою `onboarding-api`).
* **Нет config-as-code.** Конфигурация Keycloak — ручной `realm-export.json` (~3180 строк): дрейф, правки в UI теряются, ревью невозможно.
* **Смешение IdP с продуктовой логикой.** Внутри Keycloak живут magic-link-плагин (p2-inc) и рендер писем required actions; отправку писем команда self-service уже частично вынесла в отдельный сервис — именно из-за неудобства поддержки и деплоя внутри Keycloak, что подтверждает целевой принцип «чистый IdP».
* **Нет единого стандарта** сессий, MFA и подключения новых продуктов.

### Бизнес-обоснование

* **Сертификация платёжного контура** (PCI DSS, NESA, требования РФ) требует централизованного управления доступом, нативного отзыва сессий ≤ 15 минут, отказа от ROPC и от второго эмитента (собственной подписи) в цепочке логина.
* **Отщепляемость РФ**: изоляция персональных данных по регионам — регуляторное требование; общий инстанс аутентификации между регионами его нарушает.
* **Time-to-market**: платформа — greenfield; единый стандарт подключения (регистрация OIDC-клиента через MR) снимает с продуктовых команд построение собственного логин-стека.
* **Воспроизводимость**: восстановление контура аутентификации из репозитория без ручной сборки.

### Контекст

Global Platform — greenfield. Единый вход — на первом этапе реализуется в Backoffice Portal, далее подключаются платформенные продукты, затем внешние сценарии. Существующий MENA-инстанс Keycloak продолжает обслуживать текущие продукты и в рамках этого RFC не изменяется.

AS-IS (MENA), реальная цепочка инвертированной федерации:

**AS-IS (MENA): реальная цепочка инвертированной федерации.**

#### Цели / Не-цели

**Цели:**

* 100% входов пользователей в продукты Global Platform — через единый IdP.
* Нативный отзыв сессий ≤ 15 минут (требование ИБ).
* Изоляция персональных данных по регионам, отщепляемость РФ.
* Единый стандарт подключения продукта: регистрация OIDC-клиента через MR.
* Конфигурация контура аутентификации воспроизводима из git.

**Не-цели:**

* **Авторизация** (RBAC/ABAC, PDP, каталог прав) — предмет отдельного RFC. Здесь фиксируется только граница: тонкие права не входят в состав токена; предопределённые грубые роли в токене — см. «Состав токена».
* **Межсервисная аутентификация (m2m)** — предмет отдельного RFC. Здесь фиксируется только место m2m-клиентов в топологии (realm `internal`).
* Миграция пользователей существующего MENA-инстанса.
* Federation банков-партнёров (realm `partners` закладывается как скелет, подключение — при появлении первого партнёра).

### Связь с ранее отклоненными решениями

* Развивает EPIC-001 — SSO-вход в бэкофис.
* Отменяет ранний план (до 2026-06-16) «realm на существующем MENA-инстансе + миграция» — см. Альтернативы.
* Этот RFC — первый в серии платформенных RFC; RFC по авторизации опирается на него.
* Решения по авторизации и m2m выносятся в последующие RFC; спорные точки аутентификации — в дочерние ADR (см. Предлагаемое решение).
* Параллельно идёт работа по RBAC Backoffice Portal («Аутентификация пользователей поддержки продукта») — enforcement ролей остаётся в контуре авторизации (отдельный RFC).

## Предлагаемое решение

### Принципы: Keycloak — чистый IdP

Auth-взаимодействие остаётся в Keycloak, всё остальное выносится наружу:

| Внутри Keycloak | Снаружи |
| --- | --- |
| Форма логина, MFA, соц-редирект | Отправка писем (SPI → Notifications) |
| Выпуск и подпись токенов, JWKS | Рендер шаблонов писем |
| Сессии, нативный отзыв | Magic-link (не переносится) |
| Token Exchange (RFC 8693) | Брендинг как бизнес-логика |

Кастомизация аутентификации допускается только через штатные точки расширения Keycloak (Authenticator SPI, темы). Если требуется auth-кастомизация, невыразимая через SPI/темы, — это триггер пересмотра решения (см. дочерний ADR по auth-слою `onboarding-api`).

### Топология инстансов

Новый чистый инстанс Keycloak **на каждый регион** (MENA, РФ, Мексика — по мере выхода). Существующий MENA-инстанс не изменяется. Версия — **26.6.3**; политика обновлений — см. «Компромиссы и технический долг». Брендинг под конкретного партнёра (white-label) — отдельный инстанс; партнёр в общем инстансе получает общий брендинг.

### Топология realm

| Realm | Субъекты | Назначение |
| --- | --- | --- |
| `employees` | Сотрудники | Вход в Backoffice Portal |
| `merchants` | Мерчанты | Личный кабинет (web) + мобильное приложение |
| `internal` | Сервисные аккаунты | m2m-клиенты (детали — отдельный RFC) |
| `api-keys` | Внешние разработчики | Public API по API-ключам |
| `partners` | Банки-партнёры | Identity Brokering (скелет, позже) |

Имена realm — без префиксов. Тип субъекта определяется realm-ом и виден в `iss` токена.

### Клиенты и потоки по типам

| Клиент | Realm | Тип | Поток | MFA | Сессия |
| --- | --- | --- | --- | --- | --- |
| `shell` | `employees` | confidential | Authorization Code + PKCE (S256) | обязательна (TOTP) | access 15 мин / refresh 8 ч |
| `lk-web` | `merchants` | confidential | Authorization Code + PKCE | опционально (по тарифу) | access 15 мин / refresh 24 ч |
| `mobile-app` | `merchants` | public | Device Authorization Grant (RFC 8628), без webview | SMS / TOTP | offline-токены; TTL — согласование с ИБ |
| Public API | `api-keys` | service accounts | `X-Api-Key` → SHA256-lookup → JWT | — | короткоживущий JWT |

Общие правила: ROPC (Direct Access Grants) выключен у всех интерактивных клиентов; точные `redirect_uri`; PKCE обязателен для всех Authorization Code потоков. Отзыв: JWT-валидация по JWKS для обычных запросов, introspection — для критичных операций платёжного контура.

Целевой поток (TO-BE):

**TO-BE: целевой поток аутентификации.**

### Состав токена

Минимальный состав claims access-токена: `sub`, `iss` (realm = тип субъекта), `azp`. Дополнительно:

* **`tenant_id` / `company_id`** — зашиты в клеймах пользователя (realm `merchants` и `api-keys`). Один мерчант принадлежит ровно одной компании — multi-company не поддерживается.
* **Предопределённые грубые роли** — в токене (`realm_access`), нередактируемые: `employees` — `global_admin`, `global_auditor` (read-only); `merchants` и `api-keys` — `company_admin`, `company_auditor`. Роли добавляются в токен, но на API Gateway не проверяются: enforcement — целиком в контуре авторизации (отдельный RFC).
* **Тонкие права** в токен не входят.
* **Внутренний (exchanged) токен** дополнительно валидируется каждым сервисом (подпись, `iss`, `aud`, срок действия) — zero-trust: обмен на API Gateway доверия не создаёт.

### Сквозной поток токенов

Один запрос пользователя проходит через два токена — внешний (edge) и внутренний (exchanged):

**Сквозной поток токенов: внешний (edge) и внутренний (exchanged).**

1. **Логин.** Клиент получает **внешний токен**: `iss` = realm региона, `aud=platform-api`, `azp` = OIDC-клиент, claims из «Состава токена», TTL 15 мин.
2. **API Gateway.** Полная валидация внешнего токена (подпись по JWKS realm-а из белого списка, `aud=platform-api`, срок) и матч роута. У каждого проксируемого роута — метаданные `{audience, scope}` целевого сервиса. JWKS realm-ов кэшируется в памяти API Gateway (обновление по TTL и по kid-miss) — сетевого хопа к Keycloak на каждый запрос нет.
3. **Token Exchange (RFC 8693).** API Gateway через собственный confidential-клиент обменивает внешний токен на **внутренний** с `aud` = сервис роута и scope роута; результат кэшируется (~60 с); заголовок `Authorization` подменяется. При сбое обмена — 502; внешний токен внутрь периметра не форвардится никогда.
4. **BFF / сервис.** Самостоятельно валидирует внутренний токен (zero-trust) и берёт principal из claims (`sub`, tenant, `act` при LoginAs). Прямой вызов сервиса внешним токеном отбивается несовпадением `aud`.

|  | Внешний токен | Внутренний токен |
| --- | --- | --- |
| Выпускает | Keycloak (realm пользователя) | Keycloak по запросу API Gateway (exchange) |
| `aud` | `platform-api` | конкретный сервис (`tms`, `billing`, …) |
| `scope` | `openid` + профиль | scope роута |
| TTL | 15 мин | ≤ остатка внешнего; кэш обмена ~60 с |
| Валидирует | API Gateway | сам сервис / BFF |

### Hosted login и SSO

Вход — hosted login Keycloak с брендированной нативной темой: базовая `platform-base` и overlay-темы по Brand (`brand-<slug>`, например `brand-lifepos`, `brand-fortis`). Выбор overlay — по дефолтному Brand региона либо white-label Tenant'а. Собственная форма логина с ROPC — отклонена (см. Альтернативы); задел в теме — `kc_idp_hint` для будущей federation. Hosted login ≠ hosted registration: Keycloak владеет только identity-частью — учётка, credentials, сессии, MFA. Регистрация и онбординг мерчанта — бизнес-процесс команды онбординга и остаётся вне Keycloak; учётка создаётся на раннем шаге этого процесса, дальнейшие шаги идут под открытой сессией Keycloak. Сессия hosted login даёт SSO: вход в один продукт — вход во все. Подключение нового продукта = регистрация OIDC-клиента через MR (см. Config-as-code), без изменения кода платформы. Инварианты для любого продукта: аутентификация только через Keycloak, трафик только через API Gateway.

### LoginAs (вход саппорта от имени мерчанта)

Реализуется как **делегирование** через Token Exchange (RFC 8693), не как чистая impersonation: в токене `sub` = мерчант, `act` = сотрудник саппорта — атрибуция сохраняется для аудита (SoD, PCI DSS).

**LoginAs: делегирование через Token Exchange (RFC 8693).**

Параметры: cross-realm обмен `employees → merchants`, токен выпускает realm `merchants`, короткий TTL, refresh выключен, каждое действие пишется в неизменяемый аудит. Требует Keycloak ≥ 26.5 (Standard Token Exchange GA — выполнено на 26.6.3). Конфигурация доверия и перечень запрещённых операций в режиме LoginAs — отдельный RFC и согласование с ИБ.

### Config-as-code

Два репозитория с независимыми pipeline:

| Репозиторий | Содержимое | Триггер деплоя |
| --- | --- | --- |
| `platform-keycloak-image` | Dockerfile + SPI JAR | rebuild образа → rolling restart (редко) |
| `platform-keycloak-config` | YAML realm/clients (`keycloak-config-cli`) | apply через Admin API, **без рестарта** |

* Секреты — Vault / GitLab CI variables, подстановка при apply; в репозитории секретов нет.
* Онбординг команды = MR с YAML OIDC-клиента: срабатывает только config-pipeline, Keycloak не перезапускается.
* Деплоит и поддерживает команда Admin Platform; инфраструктура предоставляет namespace, registry, Helm.

### Подключение нового клиента (продукта)

Подключение продукта — два коротких MR: OIDC-клиент в Keycloak и роут на API Gateway. Ручной доступ к Keycloak Admin Console не нужен.

**Шаг 1 — OIDC-клиент** (MR в `platform-keycloak-config`):

1. `make new-client` (или skill `new-client` в Claude Code) — указываются id, тип клиента (SPA / backend-сервис / сервис с token exchange), realm и redirect URI. Скрипт сам генерирует корректную OIDC-конфигурацию: поток Code + PKCE для браузерных клиентов, scope, небезопасные grant-типы выключены.
2. Секрет — если нужен: скрипт печатает готовую команду записи в Vault, выполняет её команда Admin Platform при ревью MR (у команд-потребителей доступа к Vault-путям Keycloak нет; секрет в git не попадает).
3. Гейт MR: офлайн-валидатор (`redirect_uri`, поток, scope, отсутствие plaintext-секретов) + ревью Admin Platform по короткому чеклисту.
4. После мержа config-pipeline применяет изменения без рестарта Keycloak.

**Шаг 2 — роут на API Gateway** (MR в `platform-gateway-public`):

`make new-route` (или skill `new-route`) — указываются клиент, путь и адрес сервиса; цикл тот же: офлайн-валидатор на гейте, применение без рестарта. Сервис доступен снаружи только через route API Gateway с метаданными `{audience, scope}` (см. «Сквозной поток токенов»); прямой ingress к сервису не создаётся.

**Итог:** подключение занимает минуты; единственное ручное действие — однострочная команда в Vault, которую выполняет команда Admin Platform, а не разработчик.

**Target (вне этого RFC):** самообслуживание (заявка/портал) — часть автоматизации работы с инфраструктурой платформы; здесь фиксируется только направление.

### SPI-расширения

| Плагин | Назначение | Механизм | Когда |
| --- | --- | --- | --- |
| `auth-correlation-id-mapper` | Claim `auth_correlation_id` при выпуске/обмене токена — сквозная auth-корреляция (проверен PoC) | `Protocol Mapper SPI` | первая версия |
| `audit-provider` | Auth-события (логин, логаут, ошибки, MFA) → Kafka → Audit Log | `EventListenerProvider` | перспектива |
| `email-provider` | Вынос отправки писем в сервис Notifications | `EmailTemplateProvider` | перспектива |

До внедрения `audit-provider` auth-события доступны через штатный event log Keycloak.

`auth_correlation_id` коррелирует auth-транзакцию (выпуск → exchange → потребление), не отдельный HTTP-запрос: при попадании в кэш обмена (~60 с) один и тот же `auth_correlation_id` окажется у всех запросов, переиспользующих закэшированный внутренний токен в этом окне. Это отличает claim от per-request span/trace\_id OTel — поэтому и не называем его `trace_id`, чтобы не создавать ложных ожиданий о span-уровневой гранулярности.

Дальнейшие кандидаты (активируются решениями по открытым вопросам):

| Точка расширения | Кандидат | Триггер |
| --- | --- | --- |
| `Authenticator SPI` | SMS-OTP через внешний OTP-сервис; IP-binding сессий Shell | решение ИБ по MFA / IP-binding |
| `Protocol Mapper SPI` | Дополнительные кастомные claims | потребность потребителей токена |
| `Password Policy SPI` | Парольные политики под требования ИБ | если штатных политик не хватит |

Критерий допустимости SPI: расширение должно быть продукт-агностичным (кросс-срезовым: наблюдаемость, аудит, транспорт, auth-факторы). SPI, кодирующий продуктовую бизнес-логику или знание конкретного продукта, — запрещён; исключение оформляется только через ADR. Инвентарь SPI — бюджет обратимости (см. «Обратимость»).

Анти-паттерн: `User Storage SPI` (федерация во внешнее хранилище пользователей) — **запрещён**: повторяет инвертированную федерацию As-Is в новой форме — второй источник идентичности и скрытая зависимость логина от внешнего сервиса.

#### Почему не переносим magic-link

* Ссылка в письме — одноразовый bearer-токен в недоверенном канале: пересылается, гасится корпоративными сканерами ссылок (или, хуже, активирует вход за пользователя), легко имитируется фишингом.
* Вход по ссылке идёт в обход стандартного auth flow: MFA, brute-force protection и step-up политики к нему единообразно не применяются.
* Как единственный фактор не проходит требования к админ-доступу (PCI DSS).
* В As-Is используется плагин p2-inc keycloak-magic-link (`send_email: false` — письма шлют required actions вроде UPDATE\_PASSWORD, не сам плагин); ссылка при этом остаётся одноразовым bearer-токеном со всеми рисками выше.
* Валидный сценарий As-Is «бесшовный переход в ЛК после завершения регистрации» закрывается штатно, без magic-link: учётка создаётся на раннем шаге онбординга, дальнейшие шаги идут под открытой сессией Keycloak, финальный редирект в ЛК — обычный OIDC-flow (SSO).
* Если passwordless понадобится — штатный путь: шаг логина через Authenticator SPI + доставка через `email-provider`, либо WebAuthn/passkeys.

### Проверено PoC

* Standard Token Exchange (RFC 8693) на Keycloak 26.6.3 с подменой `audience`/`scope` — `gateway/platform-gateway-public` (YARP, .NET 10).
* Multi-realm валидация JWT на API Gateway: роутинг по `iss`, полная per-realm валидация.
* `keycloak-config-cli`: накат realm из YAML через CI, секреты — в Vault (`auth/keycloak-config`).
* Кастомный SPI (protocol mapper) в образе 26.6.3 работает при exchange (`auth/keycloak-image`).

PoC-упрощения (password grant для тестов, секреты открытым текстом, `start-dev`) в целевую конфигурацию не переносятся — см. «Компромиссы и технический долг».

### Дочерние RFC

Развилки, выносимые из этого RFC в отдельные решения:

| RFC | Предмет | Участники |
| --- | --- | --- |
| Auth-слой `onboarding-api` | Вариант A (BFF без роли IdP) vs B (сохранить кастомный OIDC). Критерий-водораздел: нужна ли auth-кастомизация вне Keycloak SPI/тем | Команда + ИБ |
| LoginAs | Конфигурация cross-realm доверия, запрещённые операции, identity chaining | Команда + ИБ |
| Offline-first мобильных | `offline_access`, тюнинг Offline Session Idle/Max, client-side decoupling от логаута | Мобильная команда + ИБ |
| API-keys realm | Service account vs custom user type; middleware на публичном API Gateway | Команда |
| Детальная конфигурация Keycloak | Полные YAML-спеки realm/клиентов/auth-flows | Команда |

### Открытые вопросы

| Вопрос | Решение за |
| --- | --- |
| Интеграция с сервисами PCI-скоупа: граница контуров, чей IdP аутентифицирует сервисы платёжного контура, точки касания (m2m, introspection, аудит) | Платёжная платформа + ИБ |
| Вариант A/B auth-слоя `onboarding-api` (дочерний ADR) | Команда + ИБ |
| MFA/OTP: native TOTP vs внешний OTP-сервис (SMS требует SPI) | ИБ + команда |
| TTL offline-токенов (`Offline Session Idle`/`Max`) под offline-first мобилку | Мобильная команда + ИБ |
| Google-логин в РФ (ограничения) — оставить или отложить | ИБ |
| Форма логина: нативная тема Keycloak vs прокси-API — с учётом PCI и брендинга | ИБ + команда |
| Брендинг формы под партнёров (динамический/статический) | Продукт |
| IP-binding сессий Shell: custom SPI или отказ | ИБ |
| Single logout — нужен ли (front-channel logout включён) | Команда |
| `api-keys`: service account vs custom user type | Команда |
| Режим `import.managed.*` в `keycloak-config-cli` (full vs no-delete); судьба ресурсов, заведённых вне YAML | Команда |
| Vault из GitLab CI: пути, механизм аутентификации | Инфраструктура |
| Доменное имя Keycloak-инстанса | Команда + инфраструктура |
| TTL access-токена 15 мин — делать ли настраиваемым | ИБ |
| Поток мобильного приложения: Device Authorization Grant (RFC 8628) vs Authorization Code + PKCE через системный браузер (RFC 8252). Device Flow выбран из-за возражения Network против открытия браузера в приложении; стандартный native-паттерн — Auth Code + PKCE | Мобильная команда + ИБ Network |
| Гранулярность auth-аудита: достаточно ли ИБ `auth_correlation_id` на auth-транзакцию (кэш обмена ~60 с) или нужен per-request идентификатор (= отказ от кэша обмена либо отдельный request-scoped механизм) | ИБ |
| Перечень «критичных операций» с introspection: критерий отнесения, владелец списка, профиль POS-подобных клиентов (высокая частота коротких операций) | ИБ + команда |

### Критерии решения (архком)

* **Сертифицируемость**: покрывает ли решение требования PCI DSS / NESA / РФ на платёжном контуре (отзыв ≤ 15 мин, MFA, аудит, отказ от ROPC).
* **Изоляция регионов**: достигается ли отщепляемость РФ без пересборки архитектуры.
* **Time-to-market**: стоимость подключения нового продукта (цель — один MR).
* **Стоимость владения**: инфраструктура на регион + дисциплина обновлений OSS против стоимости N собственных логин-стеков.
* **Обратимость**: возможность замены IdP — проверяется границами из подсекции «Обратимость»: adapter-граница, версионируемый контракт claims, строгий RFC 8693, SPI-бюджет, инвентарь непереносимого с оценкой стоимости.

## Альтернативы

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
| --- | --- | --- | --- |
| ✓ **Новый чистый инстанс Keycloak на регион** | Изоляция персданных, сертифицируемость, отщепляемость РФ, greenfield без легаси | Новая инфраструктура на каждый регион | **Выбрана** |
| Realm на существующем MENA-инстансе + миграция | Быстрый старт | Связанность с чужим prod, риск для работающих продуктов, миграция пользователей | Отклонена (план до 2026-06-16): риск и связанность перевешивают скорость |
| Развитие самописной аутентификации (onboarding-api как OIDC-провайдер) | Максимальная свобода auth-flow, IdP-агностичность | Двойной IdP, ROPC, второй эмитент со своим ключом, Python в сертифицируемом контуре | Против принципа «чистый IdP»; несовместимо с требованием отзыва ≤ 15 мин и сертификацией |
| SaaS IdP (Auth0, AWS Cognito, Okta) | Нет своей инфраструктуры, managed-обновления | Персданные у внешнего провайдера (блокер для РФ), стоимость на MAU, vendor lock-in, ограничения кастомизации | Регуляторная изоляция РФ недостижима; стоимость растёт с базой мерчантов |
| Ничего не делать | Нет затрат сейчас | Каждый продукт строит свой логин-стек: N реализаций MFA/сессий/отзыва, провал сертификации платёжного контура, нет SSO | Стоимость бездействия превышает стоимость платформенного решения уже на втором продукте |

## Компромиссы и технический долг

### Компромиссы

* **Кастомизация ограничена** точками расширения Keycloak (Authenticator SPI, темы). Осознанно: свобода кастомного auth-flow обменяна на сертифицируемость и один IdP.
* **Рестарт при изменении SPI/UI** (изменение YAML-конфигурации рестарта не требует). Риск принудительного логаута мобильных приложений митигируется offline-токенами, persistent user sessions (дефолт с v26) и rolling/blue-green деплоем.
* **Keycloak OSS без LTS**: поддерживается только актуальный минор (предыдущий умирает за считанные дни после релиза следующего).

### Обратимость

Декларация «обратимость через стандартные OIDC/OAuth 2.1 потоки» размывается по мере накопления SPI, тем и exchange-семантики. Чтобы она оставалась проверяемой, фиксируются границы:

* **Adapter-граница.** Продукты, BFF и API Gateway зависят только от стандартного контракта: OIDC discovery, JWKS, token endpoint, grant RFC 8693. Зависимости от Keycloak-специфики (admin API, формат realm-конфигурации, нестандартные параметры exchange) допустимы только внутри платформенного слоя (Admin Platform), никогда — в продуктовом коде.
* **Контракт claims.** Состав и формат токена (см. «Состав токена») — версионируемый контракт платформы. Keycloak-специфичный `realm_access` не входит в контракт: потребители читают роли через нейтральный маппинг (dotnet-шаблон BFF из Integration Kit), чтобы смена IdP не трогала продуктовый код.
* **Token Exchange — строго RFC 8693.** Только стандартный grant (`urn:ietf:params:oauth:grant-type:token-exchange`, `audience`, `scope`); проприетарные расширения exchange Keycloak не используются.
* **SPI-инвентарь (бюджет).** Допустимые расширения исчерпывающе перечислены в «SPI-расширения» (1 активный, 2 перспективных, 3 кандидата). Расширение инвентаря — только через ADR.
* **Инвентарь непереносимого.** Темы (FreeMarker), YAML `keycloak-config-cli`, SPI JAR переписываются при смене IdP; оценка — темы и конфигурация в неделях, SPI — пропорционально инвентарю (ещё один аргумент держать его коротким). Продуктовый код при смене IdP не меняется — это и есть проверяемое содержание обратимости: замена IdP — проект платформенной команды, а не всех продуктов.

### Технический долг

| Долг | План устранения |
| --- | --- |
| Нет LTS у Keycloak OSS | Политика обновлений: новый минор — 4 недели, патч безопасности — 2 недели; мониторинг релизов; обновление = пересборка образа + smoke-тест SPI + rolling deploy |
| IP-binding сессий Shell нативно не поддержан | Custom SPI или осознанный отказ — открытый вопрос с ИБ |
| Принудительный логаут offline-first мобильных при отзыве/смене пароля | Дочерний ADR: client-side decoupling — локальные данные и sync-queue не зависят от auth-токена |
| PoC-шорткаты (password grant, секреты в YAML, `start-dev`, `sslRequired: none`) | Ликвидируются при переводе конфигурации в целевые репозитории: prod-режим `start`, все секреты в Vault, Direct Access Grants выключен |

## Ресурсы и нагрузка

### Нагрузка

Профиль: пики логинов по утрам, валидация JWKS кэшируется на потребителях, Token Exchange на API Gateway (кэш ~60 с по PoC).

Узкое место — не ноды Keycloak, а PostgreSQL: Keycloak пишет сессию в БД на каждый логин и refresh (это дефолт с v26, отключать не стоит — иначе теряем отзыв ≤ 15 минут). Поэтому просто добавить ноды не поможет — каждая новая нода добавляет соединения к той же БД. Меры:

* **Ограничить пул соединений и поставить PgBouncer** между Keycloak и PostgreSQL — самая важная мера: без неё автоскейлинг Keycloak быстро выест весь пул соединений БД.
* **Отдельный инстанс PostgreSQL** только под Keycloak, не общий с продуктовыми базами.
* **Меньше лишней записи**: не форсировать ротацию refresh-токена без необходимости; `offline_access` — только мобильному клиенту.
* **Если не хватит** — эскалация: внешний Infinispan-кэш перед БД (снимает часть нагрузки, БД остаётся источником истины) — отдельный ADR с инфраструктурой.

### Ресурсы

На регион: инстанс Keycloak (k8s namespace, Helm), PostgreSQL (предоставляет инфраструктура), доступ к Kafka (аудит), Vault. Команда Admin Platform деплоит и сопровождает самостоятельно.

## Информационная безопасность

* Нативный отзыв сессий ≤ 15 минут ко всем сессиям — ключевое требование ИБ, выполняется единым IdP без второго эмитента в цепочке.
* Отказ от ROPC (исключён из OAuth 2.1) и от второго эмитента с собственным ключом в цепочке логина.
* MFA обязательна для сотрудников (`shell`), для мерчантов — по тарифу/риску.
* PKCE S256 обязателен; точные `redirect_uri`; webview запрещён для мобильного потока.
* Все auth-события — в неизменяемый Audit Log через `EventListenerProvider` → Kafka; LoginAs атрибуцируется через `act`-claim (SoD, PCI DSS).
* Строгий PCI-scope — только платёжный контур; introspection для критичных операций.
* Секреты клиентов — Vault, ротация; изоляция: секрет = отдельная CI-переменная.
* RFC до архкома проходит предварительное ревью ИБ.

### Зависимости от других команд

* **Инфраструктура**: namespace/registry/Helm, PostgreSQL, Kafka-кластер, доступ Vault из GitLab CI, доменное имя инстанса, GitLab-раннеры для пайплайнов группы (текущий блокер деплоя Keycloak на dev — этап 0).
* **ИБ**: предварительное ревью RFC; TTL offline-токенов; механизм MFA/OTP; требования к аудиту (retention, WORM, события PCI).
* **Мобильная команда**: Device Flow без webview, offline-токены, поведение при рестарте инстанса.
* **Платёжная платформа**: согласование границы PCI-скоупа и точек интеграции (условие архкома).

#### Влияние на команды / юниты

| Команда | Влияние |
| --- | --- |
| Продуктовые команды | Подключение через MR с OIDC-клиентом; собственные логин-стеки не строятся |
| Frontend (Shell, ЛК) | OIDC Authorization Code + PKCE против hosted login; своя форма логина не разрабатывается |

### Критерии готовности

* Вход в Shell и ЛК — через Keycloak, MFA включена для `employees`.
* Конфигурация воспроизводится из репозитория на чистом инстансе одним pipeline.
* Auth-события доставляются в Audit Log.
* Подключение тестового продукта выполнено по документации без участия Admin Platform.
* Нагрузочный тест пика логинов пройден до вывода в prod (профиль и пороги — с инфраструктурой).

### Миграция / раскатка

Greenfield: продукты подключаются к новому контуру по мере готовности, существующий MENA-инстанс не изменяется — обратной миграции не требуется. Откат на любом этапе = продукт остаётся на текущем механизме входа; конфигурация инстанса восстанавливается из репозитория на любой хеш коммита. До готовности prod-инфраструктуры работаем на dev-инстансе.

### Эксплуатация

Класс сервиса — **Mission Critical**: недоступность входа = недоступность всех продуктов платформы.

## Метрики успеха

* 100% входов в продукты Global Platform — через единый IdP.
* Подключение нового продукта — один MR, без изменений кода платформы.
* Отзыв сессии распространяется ≤ 15 минут.
* Восстановление контура аутентификации из git — без ручных шагов.
* Частота rebuild `platform-keycloak-image` не растёт со временем (рост = сигнал, что продуктовая логика течёт в платформу).

## Проблема и контекст

### Проблема

Сотрудники Life Pay используют ChatGPT и Claude через личные аккаунты в рабочих задачах. Это создаёт три проблемы:

1. **Утечка персональных данных.** ФИО клиентов, номера карт, паспортные и платёжные данные уходят во внешние API без контроля компании.
2. **Нет учёта расходов.** Компания не видит, кто и сколько тратит на токены; нет бюджетных лимитов.
3. **Нет единой точки входа.** Каждый сотрудник сам получает ключи — операционный хаос и неконтролируемый периметр.

Решение в виде MVP было одобрено (RFC-0007) и запущено как пилот. С тех пор оно прошло путь от Docker Compose на внешнем VPS до managed Kubernetes и доказало работоспособность. **Текущий RFC обосновывает вывод решения в Production на корпоративной PSP-Cloud-платформе Life Pay** — это закрывает оставшийся технический долг MVP и выполняет корпоративное требование compliance unification.

### Бизнес-обоснование

* **Заказчик:** техническая необходимость + Compliance/ИБ (контроль обработки ПД) + продуктовый спрос (сотрудники уже пользуются пилотом).
* **Бизнес-цель:** дать сотрудникам безопасный доступ к лучшим LLM без утечки ПД клиентов во внешние сервисы; перевести стихийное использование личных аккаунтов в контролируемый и учитываемый периметр.
* **Стоимость бездействия:** продолжение неконтролируемой передачи ПД клиентов во внешние API (риск по 152-ФЗ и для платёжных данных), отсутствие учёта расходов, репутационный и регуляторный риск. Параллельно — невыполнение корпоративного требования о переводе всех продуктов на единую PSP-Cloud-платформу.

### Контекст

* **Текущая архитектура (AS IS):** сервис развёрнут в Yandex Managed K8s в `analytics` tenant под управлением ArgoCD (GitOps), с managed PostgreSQL, ingress-nginx + cert-manager. Egress к провайдерам — через корпоративный Squid-proxy (`HTTPS_PROXY`). Цепочка контейнеров: Open WebUI → PII Masker → LiteLLM.
* **Используемые технологии:** Open WebUI v0.8.10, собственный PII Masker (Python/FastAPI, Microsoft Presidio + SpaCy `ru_core_news_md`), LiteLLM, PostgreSQL, S3, Kubernetes, Helm.
* **Зависимости от других систем:** Anthropic API, OpenAI API, корпоративный HR-бот «Эйчарка» (платформа Base44), платформенные сервисы PSP-Cloud (Vault, umbrella CI, shared k8s-кластеры).
* **Ограничения:** регуляторные — 152-ФЗ (обработка ПД), требования к платёжным данным; корпоративное требование compliance unification; данные клиентов должны оставаться в РФ-юрисдикции.

## Предлагаемое решение

Вывести LLM Gateway в Production на shared PSP-Cloud-платформе Life Pay (Yandex Managed K8s, кластер `PSP-Cloud-prod`, namespace `llm-gateway-prod`), мигрировав данные с текущего prod в `analytics` tenant. Прикладная логика (Open WebUI → PII Masker → LiteLLM + skill-runtime) переносится без изменений; меняется инфраструктурный слой: ArgoCD → umbrella CI Life Pay, k8s Secret → HashiCorp Vault, kube-prometheus → платформенный мониторинг. Egress к внешним LLM-провайдерам сохраняется через корпоративный forward-proxy (Yandex-подсети не имеют прямого доступа в Anthropic/OpenAI).

**High-level flow.** Сотрудник обращается к веб-интерфейсу по HTTPS. Запрос проходит через PII Masker — единственную точку выхода контента наружу, — где последовательно выполняются: проверка бюджетных лимитов (fail-closed), обезличивание ПД и маршрутизация по выбранной модели. Во внешние API (Anthropic/OpenAI) уходит **только обезличенный текст**. Оригинал диалога сохраняется в истории Open WebUI (managed PostgreSQL в РФ).

**Ключевые технологии:** Microsoft Presidio + SpaCy + 19 кастомных распознавателей под российские документы (паспорт, СНИЛС, ИНН, ОМС, БИК, КПП, ОГРН, банк. счёт, карта), HashiCorp Vault (Agent Injector), Yandex Managed PostgreSQL (HA + PITR), Yandex Object Storage.

После cutover'а старый prod в `analytics` tenant держится scaled-to-0 как rollback-target 7 дней, затем decommission.

## Альтернативы

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
| --- | --- | --- | --- |
| **Корпоративный аккаунт ChatGPT/Claude** | Быстро, без разработки | Не решает проблему ПД в промптах; нет учёта по пользователям; нет гибкости по моделям | Не закрывает главный риск (утечка ПД) |
| **Локальная LLM (Ollama + Llama/Mistral)** | Данные не покидают периметр | Качество ниже Claude/GPT; требует GPU (CAPEX); долгий time-to-value | Неприемлемое качество и стоимость |
| **Azure OpenAI / Yandex GPT** | Managed, в облаке | Долгие согласования; нет Anthropic в Azure; Yandex GPT уступает по качеству | Нет нужных моделей, медленный выход |
| **Остаться в `analytics` tenant** | Уже работает | Не выполняет требование compliance unification; команда сопровождает отдельный ArgoCD/мониторинг | Противоречит корпоративному требованию о единой PSP-Cloud-платформе |
| **Ничего не делать** | — | Продолжение неконтролируемой передачи ПД, регуляторный риск, нет учёта расходов | Неприемлемый риск по 152-ФЗ |

## Компромиссы и технический долг

### Компромиссы

* **Историческая копия оригинального промпта в БД (короткое окно ~10 сек).** Open WebUI сохраняет сообщение до передачи в PII Masker; фоновый sweeper масковит его в managed PG в течение ~10 секунд после сохранения (см. «Информационная безопасность → Sweeper истории»). Полное отсутствие оригинала в БД возможно только через форк Open WebUI — нецелесообразно.
* **Исключение для юр-отдела (Ассистент без маскирования).** Юристы по бизнес-задаче обрабатывают реальные ПД клиентов; для них sweeper пропускает чаты с моделью `no-mask-assistant` (двойной гейт: allowlist пользователей + белый список моделей). Оригинал сохраняется — это осознанная бизнес-необходимость.
* **Обезличивание применяется и на egress (before external API), и в БД (async sweeper).** Двойное покрытие: request path — синхронно; хранилище — асинхронно.

### Технический долг

| Описание долга | Категория | План устранения | Срок |
| --- | --- | --- | --- |
| CVE в образе pii-masker (отложены, чтобы не задерживать миграцию) | Управляемый | Bump base-image + pip-зависимостей, regression-прогон gold-датасета | ~1 день |
| Uploads в S3 без retention | Управляемый | Лимит объёма bucket'а + weekly cleanup-job (удаляет файлы старше 90 дней) | ~0.5 дня |

## Ресурсы и нагрузка

### Нагрузка

* Целевая аудитория: ~100–200 сотрудников Life Pay.
* Текущее использование: сервисом ежедневно пользуются ~20–25 человек (DAU).
* Профиль: интерактивный чат + загрузка документов; нагрузка низкая и неравномерная (рабочие часы). Для справки: за период работы в `analytics` накоплено ~15 500 записей `request_logs`.
* Реплики на окружение: PII Masker 2, LiteLLM 2, Open WebUI 1 (локальный state), skill-runtime 1–2.

### Ресурсы

* **Лимиты памяти (prod values):** PII Masker до 12Gi (пик ~3.7 ГБ/воркер при extract больших xlsx), Open WebUI 10Gi, LiteLLM 6Gi.
* **БД:** Yandex Managed PostgreSQL, 3 БД (`openwebui` / `litellm` / `analytics`), HA + PITR.
* **Хранилище:** Yandex Object Storage (S3), bucket на окружение.
* **Стоимость:** основной драйвер — расход на LLM API (Opus ~41% расходов). Контролируется лимитами: soft $40/мес на пользователя + жёсткий лимит Opus 15 запросов/нед (fail-closed). Инфраструктура — на shared PSP-Cloud-платформе (платформенные квоты).

## Информационная безопасность

* **Хранение/обработка ПД:** Да. ПД клиентов (ФИО, карты, паспорта, СНИЛС/ИНН, платёжные реквизиты) могут присутствовать во входящих промптах и файлах.
* **Публичное API:** публичный ingress + self-service `/auth/*` (whitelist домена `life-pay.ru`) + rate-limit на `/api/v1/auths/signin`; административные `/admin/*` — под Bearer-токеном.

**Основные угрозы:**

* Утечка ПД клиентов во внешние LLM-API.
* Компрометация хранимой истории диалогов (содержит оригинальный текст с ПД).
* Компрометация секретов / API-ключей.

**Меры защиты:**

* **Обязательное обезличивание до egress** — PII Masker является единственной точкой выхода контента; во внешние API уходят только токены `[ИМЯ]`, `[БАНКОВСКАЯ_КАРТА]` и т. п. Движок: Microsoft Presidio + SpaCy `ru_core_news_md` + 19 кастомных распознавателей российских документов. Качество защищено регрессионным gold-датасетом (`test_gold_dataset.py`): набор реальных сценариев утечки, тест падает при появлении оригинального значения ПД в выводе — проходит на 100%.
* **Async PII sweeper истории в БД** — фоновый процесс маскирует пользовательские сообщения в `openwebui.chat`/`memory` в течение ~10 секунд после сохранения. Реализация: `chat_pii_sweeper.py` (asyncpg + Odyssey-совместимый pool), fcntl-file-lock guard (один sweeper на pod), per-chat cooldown по `updated_at` (не re-обрабатываем chat пока он не изменился). Bypass для юр-отдела: чаты с моделью `no-mask-assistant` не sweep'ятся (см. «Компромиссы»).
* **Резидентность данных в РФ** — managed PostgreSQL и S3 в Yandex Cloud; во внешние сервисы исходные ПД не передаются.
* **Транспорт:** TLS на ingress (cert-manager + Let's Encrypt); внутрикластерный трафик в private network PSP-Cloud.
* **Ingress hardening:** rate-limit на `/api/v1/auths/signin` (защита от брутфорса), CSP-заголовок + скрытие `Server`/`X-Powered-By`, CORS ограничен своим доменом, срез клиентских identity-заголовков (`X-OpenWebUI-User-*`, защита от spoofing). Опасные / неиспользуемые эндпоинты Open WebUI (SSRF `/retrieval/process/web`, memory-poisoning `/memories/add`, user enumeration `/users/search`, tools source disclosure `/tools/`) закрыты через sinkhole handler'ы в pii-masker (возвращают 403 + audit-log).
* **Секреты:** HashiCorp Vault (KV v1, Agent Injector) — не в репозитории и не в k8s Secret; ротация без передеплоя образа. Отдельные ключи для JWT / PII bypass / tools API (secret-separation guard при старте: сервис не поднимается при коллизии).
* **Доступ:** регистрация только для доменов из whitelist (`PROVISION_EMAIL_DOMAIN`, дефолт `life-pay.ru`); admin-операции — Bearer-токен; пароли — bcrypt.
* **Бюджетный gate fail-closed** — превышение жёсткого лимита Opus блокирует запрос (защита от неконтролируемого расхода).
* **Приватность метаданных наружу:** идентификатор пользователя (email), передаваемый во внешний HR-бот «Эйчарка» (Base44 SaaS), заменяется на HMAC-хэш (стабильный per user), реального корпоративного email наружу не уходит.

**Остаточные риски** (вынесены в техдолг, согласуются с ИБ/Compliance): обезличивание построено на NER и по природе технологии не гарантирует 100% recall на нетипичных формулировках, не покрытых gold-датасетом; митигируется расширяемым набором распознавателей и мониторингом.

Детальное моделирование угроз: согласование с ИБ (А. Толстых) и Compliance (Д. Карпова) — в рамках ревью данного RFC.

### Sweeper истории — детали реализации

* **Триггер:** каждые 10 секунд читает `chat.updated_at > watermark`, батч до 100 строк.
* **Что маскируется:** `chat.title` (top-level column), `chat.chat.title` (nested в JSONB), `chat.chat.history.messages.*.content` для role=user, legacy `chat.chat.messages[]` для role=user, `memory.content`.
* **Что не трогается:** сообщения ассистента, system-роль, premasked-sentinel'ы из file-upload path (уже прошли pii-masker), чаты юр-отдела (модель `no-mask-assistant`).
* **Многопоточность/scale:** fcntl-lock guard — один активный sweeper на pod (в pod до 4 uvicorn workers, sweeper только у первого получившего lock). При 3 replicas — 3 sweeper'а на кластер, не 12. Верифицировано после инцидента 09.07.2026.
* **Идемпотентность:** повторный проход по уже маскированной строке — no-op (masker не подхватывает placeholder'ы; unit-тест `test_idempotency_second_pass_is_noop`). Per-chat cooldown исключает re-scan chat'а до следующего реального `updated_at` bump'а.
* **UX-компромисс:** пользователь при перезагрузке чата видит `[ИМЯ]` вместо своего оригинала. Compliance-friendly; для регулярных сотрудников приемлемо; для юр-отдела — bypass через `no-mask-assistant`.

Во внешние API уходит **только обезличенный текст сообщений** (роли user/system/tool). **Не передаются:** полный PAN, сырые файлы, сырые логи, полные идентификаторы, секреты. ### Сегментация и hardening

* **Контейнеры non-root** — pii-masker переведён на uid 1000 (`securityContext: runAsNonRoot`, drop ALL caps); upstream-образы (Open WebUI/LiteLLM) — по возможности через securityContext на уровне пода.
* **NetworkPolicy default-deny + allow-list** — helm-манифест `deploy/helm/templates/networkpolicy.yaml` (за флагом `networkPolicy.enabled`), допустимые потоки задокументированы в шаблоне. Активация — на стороне DevOps при валидации сетевых селекторов.
* **Egress** — через корпоративный forward-proxy (`HTTPS_PROXY`/`NO_PROXY ⊇ .svc.cluster.local` из Vault); Yandex-подсети без прямого доступа в Anthropic/OpenAI.

### Единые точки отказа (SPOF)

**На нашей стороне:**

* **Open WebUI — 1 replica.** Локальный state, upstream не поддерживает multi-replica. При падении pod'а UI недоступен на ~1–2 мин пока идёт restart (защищено startupProbe с окном 10 мин на инициализацию, чтобы kubelet не убил pod во время долгого Alembic-миграционного старта).

**Внешние зависимости (не под нашим контролем, но SPOF для сервиса):**

* **Anthropic API** — при недоступности не работают модели Claude (~60% трафика).
* **OpenAI API** — при недоступности не работают модели GPT (~40% трафика).
* **Base44 (Эйчарка)** — при недоступности не работает HR-бот; остальные модели работают.

**НЕ SPOF** (защищено платформой/дублированием):

* **Корпоративный forward-proxy** — AWS NLB + 2 EC2-инстанса, при падении одного трафик уходит на второй (уже развёрнут на PSP-Cloud-инфре и на staging; на текущем prod в `analytics` tenant — старый single-VM, миграция на HA-вариант происходит вместе с cutover'ом на PSP-Cloud).
* Managed PostgreSQL — HA + PITR (реплики + автоматический failover на стороне Yandex).
* Object Storage (S3) — managed, репликация на стороне Yandex.
* HashiCorp Vault — платформенный shared сервис PSP-Cloud (HA).
* Ingress-nginx — multi-replica платформы.
* PII Masker, LiteLLM, skill-runtime — по 2 реплики с anti-affinity (разные ноды/зоны).

## План реализации

* **Этапы:**
  1. Phase 1 — dev на PSP-Cloud (настройка CI/Vault/values, sync кода форка, ingress paths) — **выполнено**, протестировано на dev.
  2. Pre-cutover prep — заполнение Vault prod, тренировочный pg\_restore, partial S3 sync, снижение DNS TTL, проверка TLS.
  3. Cutover (окно ~30–40 мин по runbook): stop traffic → финальный pg\_dump 3 БД → restore в managed PG PSP-Cloud → sanity row counts → S3 delta sync → `Helm deploy prod` → `patch-webui-config:prod` → DNS flip → smoke E2E.
  4. 7-дневное rollback-окно (старый prod scaled-to-0) → decommission `analytics`.
  5. Post-cutover: CVE-фикс образа pii-masker.
* **Оценка трудозатрат:** разработка/настройка PSP-Cloud-окружения завершена (Phase 1). Остаётся cutover (~0.5 рабочего дня окна + сопровождение) и 7 дней стабилизации.
* **Зависимости от других команд:** DevOps/Платформа PSP-Cloud (кластер, Vault, umbrella CI, DNS); ИБ и Compliance (согласование обработки ПД); координатор архсовета (слот).
* **Критерии готовности (DoD):** данные мигрированы (row counts совпадают с источником); 6 моделей + «Ассистент ГФД» + «Эйчарка» отвечают; обезличивание подтверждено на реальном примере; smoke E2E зелёный; мониторинг и алерты настроены на namespace `llm-gateway-prod`.

## Пересмотр решения

**Дата первого одобрения:** [2026-04-03 *(RFC-0007, MVP)*](https://bz.incdb.team/pages/viewpage.action?pageId=3415736376)

**Причина пересмотра:** Переход на стадию Production

### Что изменилось

* **ИТ-ландшафт:** решение прошло путь MVP → managed Kubernetes (`analytics` tenant, ArgoCD, managed PostgreSQL, корп Grafana) → **вывод в Production на shared PSP-Cloud-платформе Life Pay** (Vault, umbrella CI). Закрыт весь инфраструктурный техдолг MVP из RFC-0007 (внешний VPS, единый PostgreSQL без HA, NOPASSWD docker в CI, watchdog/ntfy.sh, HTTP-proxy). Egress к внешним LLM сохраняется через корп forward-proxy — принципиально, поскольку Yandex-подсети не имеют прямого доступа в Anthropic/OpenAI.
* **Команды и владение:** сопровождение инфраструктуры переходит на платформенный стек PSP-Cloud; команда перестаёт поддерживать кастомный ArgoCD и отдельный kube-prometheus.
* **Технологии:** добавлены self-service авторизация (signup/forgot/reset с email-верификацией), cost-control (soft $40/мес + жёсткий лимит Opus 15/нед), Agent Skills («Ассистент ГФД»), интеграция с HR-ботом «Эйчарка» (Base44), extract-and-mask файлов. Секреты переведены в HashiCorp Vault.
* **Безопасность (после RFC-0007):** проведён внешний penetration test (19–22.06.2026, 22 findings), все закрыты — код-фиксами, ingress hardening'ом (CSP, rate-limit, header strip, CORS restrict), sinkhole endpoint'ами (SSRF/memory-poisoning/enumeration/tools source), sweeper'ом истории в БД (закрытие H-05: PII теперь маскируется в БД в течение ~10 сек, а не хранится вечно), Squid ACL и декомиссией YC-мостовой VM. HMAC-хэш идентификаторов пользователей во внешние сервисы (Base44). Bypass для юр-отдела (модель `no-mask-assistant`).
* **Требования:** корпоративное требование compliance unification (все продукты — на единой PSP-Cloud-платформе); сохраняются требования 152-ФЗ и к платёжным данным, усиленные резидентностью данных в РФ, расширенным набором распознавателей российских ПД и снятием остаточного риска долгоживущей истории с ПД в БД.

### Вывод автора

Решение остаётся актуальным; подход подтверждён пилотом и готов к выводу в Production. Корректировка — инфраструктурная (перенос на PSP-Cloud-платформу) без изменения прикладной логики обезличивания и учёта расходов.
